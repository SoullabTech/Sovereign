## Two observations, offered — not resolved

### 1. Option A is precondition-light *by construction*, and that is the substantive difference

The audit's unmet preconditions attach to **v1**, not to Slice 0:

| | Bites Option A? | Why |
|---|---|---|
| **P1** Larry UI/UX spec reconciled | ✗ | Slice 0 builds no UI |
| **P2** Acceptance walk approved | ✗ | The walk accepts a *built surface*; Slice 0's deliverable is a negative proof |
| **P4** Schema ownership (Q-A/Q-B/Q-B′) | ✗ | Slice 0 adds no schema and does not decide projection-vs-co-equal |
| **P5** Constitution ratified | ✗ | Slice 0 cites no constitutional artifact as build authority |
| **P3** #899 | ◐ | Code complete `12e4787ee`; release unresolved |

⭐ **Option A is not merely a smaller Option B. It is the option whose preconditions are already
satisfied** — which is what makes it the evidence-producing move rather than a deferral.

### 2. ⚠️ G-a may or may not bite Option A, and this is a real question

**G-a** — *Phase 1 is failed at W8; no new implementation lane opens until Phase 1 is a finished
release object* — was explicitly **held, not lifted**.

The open question: **is Slice 0 an implementation lane at all?** Its deliverable is *evidence that a
boundary holds* — which is closer in kind to `verify-coach-field-boundaries.ts` (a verification
harness asserting a negative) than to a feature surface. Verification harnesses have not historically
been treated as implementation lanes under G-a.

⛔ **Not resolved here, and deliberately not resolved by building.** If Slice 0's proof is expressible
as a harness over existing services, Option A may clear G-a on its own terms. If it requires new
service code, it does not. **That is a founder call, and it is the one that decides whether Option A
can proceed today.**
