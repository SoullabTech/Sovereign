## Existing explicit capability registry

Current Standard 5 declares these member-facing capabilities:

- journal.create
- journal.save
- journal.dream
- astrology.reading
- astrology.transit
- pattern.detect
- pattern.show
- wisdom.surface
- wisdom.text
- relationship.reflect
- depth.explore
- depth.shadow

Observed standing from the standard:
- most are **defined but not wired**;
- `studio.transition` is wired through voice/world navigation;
- no complete suggestion → confirmation flow exists;
- capability lifecycle logging/state tracking is incomplete.

O1 therefore distinguishes:

> **Room/function exists** ≠ **orchestration contract exists** ≠ **voice/runtime invocation is wired**

## Major orchestration gaps

### G1 — Estate capability registry is incomplete
The declared registry does not yet represent the full Estate: Decisions, Reflections, Ideas, Changes, Living Field, Divination, Community, Co-lab, Anchor, and Studio-specific actions are not represented comprehensively.

### G2 — Capability IDs are not yet authority contracts
Current registry rows name world/modal/voice phrase/status, but do not yet declare:
- read effects;
- write effects;
- consent requirement;
- data membrane;
- economic class;
- research status;
- AIN dependency;
- acknowledgment/return behavior.

### G3 — Cross-Estate synthesis authority is under-specified
Living Field, Steward continuity, Relationships, Changes, Reflections, and Astrology all create legitimate demand for cross-room synthesis, but no single shared authority contract currently governs when one room's material may be used in another.

### G4 — Portal vs room vs ritual semantics are not encoded
Practices, Library, Community, Anchor, Living Field, and Studios are different architectural species, but capability orchestration currently treats “world” largely as a routing target.

### G5 — Research status is not visible to capability orchestration
No common capability contract currently marks whether a feature/output is:
- production-stable;
- experimental;
- research-derived;
- hypothesis-bearing;
- prohibited from member-facing claim elevation.

### G6 — Economic class is not visible to capability orchestration
Free / Steward / Studio / Capacity is being designed at the product level but is not part of capability metadata.

### G7 — MAIA/JARVIS/AIN boundaries are conceptually clear but not represented together
We have separate strong laws for each, but no shared descriptive object shows:
- MAIA may suggest;
- AIN may reason;
- JARVIS may work on implementation;
- Lab may study;
- member/operator remains consequential authority.
## Orchestration already working conceptually

The Estate already contains several high-quality handoff patterns:

### Decision Council
MAIA/member context → AIN council → structured result → member-facing decision history.

### Writer's Studio
Member work context → MAIA editorial conversation → bounded editorial acts → safe apply/undo/version history.

### Living Field
Explicit gathered sources → provenance-bearing field context → optional refinement → member acceptance.

### Team attention
Directed attention item → explicit open/resolve/decline → deep link to source.

These should be treated as reference patterns, not replaced by a new generic orchestration engine.

## O1 design implication

The next shared object should be a **descriptive Capability & Authority Registry**, not an execution engine.

Minimum future schema fields:

- capability_id
- human_purpose
- architectural_species
- owning_domain
- member_role
- suggest_authority
- invoke_authority
- consent_mode
- read_scope
- write_scope
- data_membrane
- AIN_reasoning_role
- JARVIS_work_role
- research_status
- economic_class
- acknowledgment
- return_target
- failure/stop behavior

The registry should describe authority already granted elsewhere. It must not become a source that grants authority by itself.
