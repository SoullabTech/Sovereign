# M0 Lane 1 — Substrate & Schema Inventory (Memory Ecology)

Date: 2026-08-09 · Branch: `feature/labtools-redesign` · READ-ONLY discovery workpaper
Method: static scan of canonical migration dirs (`database/migrations/`, `db/migrations/`, `db/supabase/migrations/`, `beta-deployment/db/migrations/`, `prisma/migrations/`) + single-pass grep of 6,769 code files (`app/ lib/ components/ scripts/ services/ backend/ __tests__/ tests/`, excluding `node_modules`, `.claude/worktrees/`, `docs/`). Writers = `INSERT INTO`/`UPDATE…SET`; Readers = `FROM`/`JOIN`. Liveness in production is explicitly NOT claimed here (another lane).

## Scope notes & caveats

- 613 distinct `CREATE TABLE` names exist across the repo including ~34 stale `.claude/worktrees/*` copies; this inventory scopes to canonical dirs only. 140 memory-bearing candidates were selected by keyword + explicit list.
- **Three competing migration lineages exist**: `database/migrations/` (current, PostgreSQL), `db/migrations/` + `db/supabase/migrations/` (legacy — Supabase-era duplicates; per project invariant Supabase is banned, these lineages are archival hazards), and `beta-deployment/db/migrations/`. Several tables are defined in more than one lineage with diverging DDL (e.g. `episodic_memories`).
- Zero-writer/zero-reader marks are static-code facts, subject to dynamic-SQL false negatives; an any-mention pass was run to catch query-builder usage (noted per table).

## Headline findings

1. **`agent_runs` and `integration_passes` have NO `CREATE TABLE` anywhere in the repo** — not in any migration lineage, script, or code file — yet `lib/services/corpusCallosumService.ts` writes to both and they are documented as Cat-6 live (Corpus Callosum). The production schema exists only in the production database. Rehabilitation gap: schema provenance is unrecoverable from source.
2. **13 tables are utterly unreferenced in code** (schema-only): `archetype_wisdom_library, bardic_link_events, bardic_telos_alignment_log, breakthrough_clusters, comms_consent, community_wisdom_contributions, consciousness_event_tasks, navigator_reflections, navigator_wisdom_patterns, neuropod_session_coherence_summary, session_voice_notes, soul_memories, user_consent_log`.
3. **Consent/deletion infrastructure is fragmented**: at least 8 consent-bearing tables (`user_consent_log` [unreferenced], `comms_consent` [unreferenced], `runtime_consent_state`, `session_consent_events`, `encounter_consent_events`, `living_field_participant_consents`, `soul_portrait_consents`, `coach_position_share_consents`) plus 4 deletion substrates (`deletion_manifests`/`deletion_manifest_scopes`, `user_deletion_log`, `provenance_tombstones`, `user_data_pause`). The two generic ones (`user_consent_log`, `user_data_pause`) are dead or near-dead in code; consent actually lives per-feature.
4. **Duplicated/competing substrates** — see §Duplicates.

## Duplicates & competing substrates

- **episodic_memories** — Defined in BOTH `database/migrations/20260115000010_episodic_memories.sql` (current) AND legacy `db/migrations/20251213_complete_memory_palace.sql` (+ supabase twin). Two DDL generations for one name.
- **relationship_essence vs relationship_essences** — Singular table (legacy `db/migrations/20251214_create_relationship_essence.sql`, 1 writer / 0 readers) vs plural (`database/migrations/20251223_create_holoflower_tables.sql`, 6 writers / 9 readers). Plural is the live one; singular is a stranded near-duplicate still written by one path.
- **Generic 'memory' stores** — `member_memory_atoms` (live, canonical) vs `soul_memories` (unreferenced) vs `ain_consciousness_memory` (referenced only by deletion routes + legacy service) vs `semantic_memories`/`episodic_memories`/`somatic_memories`/`morphic_pattern_memories` (typed stores, mostly Cat 3/4). At least four conceptual homes for 'a remembered thing about a member'.
- **Pattern stores** — `member_patterns`, `soul_patterns`, `pattern_ledger`(+`pattern_evidence`,`pattern_connections`), `journal_patterns`, `relationship_patterns`/`relationship_entry_patterns`, `user_session_patterns`, `ea_shadow_patterns`, `case_patterns` — eight-plus pattern substrates with no shared provenance model.
- **Breakthroughs** — `breakthrough_moments` vs `breakthrough_clusters` (unreferenced) vs `collective_breakthroughs` vs the live `member_memory_atoms.is_breakthrough` flag — the atoms flag is the canonical live mechanism; the three tables are parallel older substrates.
- **Markers** — `scribe_markers` vs `studio_session_markers` — both live-ish marker stores for session capture, different lineages.
- **Wisdom** — `wisdom_moments` (read by field-analytics + sovereignty routes) vs `wisdom_events`/`wisdom_nodes`/`wisdom_labels` (graph service, partial) vs `archetype_wisdom_library`/`community_wisdom_contributions` (unreferenced).
- **Consent** — Per-feature consent tables coexist with two generic dead ones (`user_consent_log`, `comms_consent`); no single consent ledger.

## Proof-ladder legend (static-evidence ceiling)

`Exists` = DDL in canonical migrations · `Connected` = code both writes and reads · `Reachable` = route-level (app/api) read+write · `Exercised/Observable/Sustained` = NOT claimable from static code; deferred to the production-liveness lane. `Correct`/`Secure` are only annotated where DDL shows an obvious gap.
