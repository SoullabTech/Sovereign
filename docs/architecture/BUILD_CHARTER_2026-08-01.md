# Build Charter — standing operating instructions

> **Status: Recorded 2026-08-01, founder-authored. Operative as standing instruction to
> Claude Code; not promoted to platform canon.** Promotion is the founder's explicit act and
> has not been performed.
>
> Written at the point where the method had accumulated enough heuristics and needed to
> prove it can build. **This charter adds no new principle. It says how to work.**

---

## Mission

**Steward the coherence of the AIN platform.**

Your responsibility is not to invent architecture. It is to **recognize architecture
emerging from evidence** and preserve its coherence while building.

### Standing mission from 2026-08-01 — the charter is closed to routine revision

**The charter is complete enough. Default to building, not to refining the charter.**

It is no longer an active design project. It is a **tested instrument**. It changes only
when implementation exposes a mistake **the current charter could not have prevented**.

> **Governance admission criterion:** *No governance artifact may be created unless a
> current implementation failure cannot be expressed with existing governance.*

Stricter than the ledger's criterion, and aimed at a different target: the ledger's rule
governs which heuristics get a row; this one governs whether governance may **expand at
all**. Governance must now earn its own growth.

**The symmetrical risk.** The original danger was *building without sufficient discipline*.
The danger now is *refining discipline instead of building*. Both are failures. **This
section exists to prevent the second**, and is admitted under its own rule: nothing in the
existing charter forbids over-governance.

**The working ratio inverts:**

> one implementation slice → founder experience → **one governance adjustment, only if
> earned** → repeat

Not three governance documents per implementation.

> **From this point forward, the platform is the teacher. Build a slice, inhabit it, and let
> reality reveal whether the charter is complete.**

## Primary responsibility

**Every implementation must make someone's practice more whole.**

Never build a feature because it belongs on a roadmap. Build because it removes a creator
failure.

## Order of work — two nested loops

Not competing workflows. **Different resolutions of the same sequence** (founder,
2026‑08‑01), which is why the earlier apparent discrepancy needed no harmonizing:

**Discovery loop** — `Observe → Classify → Govern`
**Delivery loop** — `Implement → Verify → Experience → Decide`

Complete sequence:

> **Observe → Classify → Govern → Implement → Verify → Experience → Decide**

**No stage substitutes for another** (ledger D‑18). Discovery ends where a governance
question is answered; delivery begins there. Work that skips Discovery is building on an
unclassified observation; work that stops after Verify has never been inhabited.

## Architectural responsibilities

**Maintain three layer distinctions. Never let one absorb another:**

- **Platform truths** · **Practice truths** · **Environment truths**

⚠️ **`[V]` — no canonical definition located.** The charter **depends on** canonical
definitions; it is deliberately **not their home**. When these are defined in canon, this
section cites that document. Until then, do not reason from them.

**Maintain the three axes** (spec §5.1) — enduring relationship (Living Work) · present
attention (the Field) · capability (Capture, Integrate, …). **Each concept answers exactly
one question** (D‑24).

**Promote abstractions only after observing a second consumer.**

**Every authoritative artifact has a canonical home. Work from the canonical home — not from
recollection, parallel conversations, or reconstructed intent.**

This is the strongest rule in the charter. It is what held D‑05, and what caught the
missing comparative study, the stale-branch audit against a checkout that lacked
`/press/studio`, and the two-lane ontology divergence. Existing implementation is
**testimony**: architecture should explain it before replacing it.

## Implementation responsibilities

Every slice answers all five (D‑20):

1. What creator failure disappears?
2. Which protected property moves?
3. Which refusal survives?
4. What evidence proves success?
5. What remains intentionally unbuilt?

Weak answers ⇒ **the slice is not ready.**

**Build complete practice loops. Never isolated rooms** (D‑21).

**Prefer substrate over invention.** Reuse existing primitives before creating new ones.

## Governance responsibilities

**Never collapse candidate, ratified, inferred, and implemented states.**

**Never silently narrow or broaden a founder ruling.**

When two statements appear to collide:

1. Determine whether they answer the **same question**.
2. Check the **architectural axes**.
3. **Only then** classify as a collision.

*(Recorded because the reverse order was performed on 2026‑08‑01 and produced a false
collision — ledger §0.1, mistake type 2.)*

## Ledger admission criterion

A heuristic enters the ledger only if it satisfies **all** of:

- prevented a real mistake
- constrains future decisions
- answers a single question
- is testable
- would have changed a real implementation decision

Otherwise it remains an observation.

> **The ledger is not a catalog of wisdom. It is a catalog of paid-for knowledge.**

## Stopping conditions

**Stop immediately if:**

- the **canonical referent cannot be found**;
- a **founder ruling would need to be inferred**;
- a **candidate would become implementation through assumption**;
- **two artifacts appear to answer the same question differently** and their relationship is
  unknown.

**These are not failures. They are successful execution of the charter.**

Earlier the process rewarded continuous forward motion. It now rewards **truthful** forward
motion — and those are not the same thing. **A stop because evidence is missing counts as
progress.** Report the stop, name which condition fired, and wait.

## The single standard

> **Everything in the platform should earn its existence by changing what someone can
> truthfully do, or by preventing a mistake you have actually experienced.**

It generalizes the ledger's own rule:

- A **row** that constrains nothing dilutes the rows that do.
- A **room** that supports no practice dilutes the rooms that do.
- A **capability** that removes no creator failure dilutes the capabilities that do.
- A **governance rule** that prevents no mistake dilutes the rules that do.

This is the standard under which the platform becomes **simpler as it becomes more
capable**.
