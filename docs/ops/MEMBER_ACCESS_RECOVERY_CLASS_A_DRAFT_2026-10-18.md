# Member Access recovery — Class A isolated draft

**Standing:** SOURCE CANDIDATE ONLY · founder approved an **EMAIL-ONLY initial beta implementation in the isolated Draft**, not a Class A merge, schema deployment, member send or runtime activation. Keep Draft; no founder release act recorded.

**Runtime membrane:** Both issuance and redemption refuse with HTTP 503 unless `MEMBER_ACCESS_RECOVERY_ENABLED=1`. The flag is unset by default. Fictional CI explicitly opts in. The setting does **not** itself authorize production use or schema deployment.

## Purpose

An authorized founder uses **Admin → User Management → Member Access** (also accessible through Studio Settings and Command Center) to initiate EMAIL-ONLY recovery for a selected existing member. The member sets their own password. The administrator never chooses, sees, emails or stores the replacement password. Separate from the legacy /reset-password and /api/admin/reset-member-password routes.

## Authority, scope and record

- **Founder verified member session only**: checkAdminAuth(req, ['founder']) AND via='member' and a real memberId. The shared LABTOOLS_ADMIN_PASSWORD is **not** sufficient to issue a recovery link, even though Command Center's older AuthGate accepts that secret for navigation. An operator without a real founder member session receives a clear 403; do not weaken to fix a UX failure.
- Exact approved browser Origin required on issuance and redemption; Origin:null, absent or foreign origin is rejected. Browser cookie is never treated as ownership of a targeted member without founder standing. A body-supplied member ID is only the *target*, not actor.
- Issuance transaction revalidates and locks the live founder session and target row, enforces a durable five/hour issuer ceiling, revokes earlier outstanding administrator links, and records issuer, target, the email-only method and reason, and a SHA-256 hash of a freshly generated 256-bit random bearer.
- A separate new table admin_member_recovery_tokens records issuance/delivery/redemption. It does not store the raw bearer. No actual member credentials or recovery links are written to application logs.
- **Verified current email proof:** The migration adds `members.recovery_email_verification_id`, initially NULL for ALL existing/legacy members. A PostgreSQL trigger mints a fresh unpredictable proof only when the member's existing email-verification token is consumed within its 24-hour validity. The existing POST `/api/members/verify-email` route now **consumes the still-current token atomically in one conditional UPDATE** (not SELECT(token) → UPDATE(member ID)), and sets the verified timestamp in the same statement. GET to the old direct API link now **redirects WITHOUT consuming** to a new `/verify-email` client threshold requiring a recipient click; new verification emails use `#token` (not `?token`) and legacy `?token` links are accepted by the landing page, erased from browser history and consumed by explicit POST only. The proof trigger and this endpoint correction must be shipped as a coupled Class A migration/runtime change; no part may be promoted alone. Any email change revokes the proof, sets `email_verified=false`, and retires the old verification token. Recovery issuance requires BOTH `email_verified=true` and a non-NULL fresh proof, stores the proof ID on the hashed recovery token, and redemption requires the current member proof to match the originally issued proof. An old or stale `email_verified=true` flag alone can never authorize recovery. **Existing accounts must verify their current address anew**, and those unable to reverify remain blocked; there is no silent grandfathering or private handoff.
- **Approved SMTP only:** `EMAIL_PROVIDER=smtp` must be set explicitly, and the actual selected provider must report `name='smtp'` and `isConfigured()=true`. The provider object is pinned into `sendEmail` so the legacy default to Resend, a capture provider or unknown provider cannot send this recovery email. A successful email result must include `provider='smtp'` and a provider-issued message ID, otherwise the stored token is revoked and the response fails closed.
- Email: managed SMTP provider acceptance only, NOT confirmed recipient delivery, 30-minute expiry; failed/refused acceptance revokes the link. A pending receipt is not redeemable.
- **Beta email-only law:** The Admin UI exposes no private-handoff control or copyable bearer. The issuance endpoint returns **403 for `private_handoff` even if the caller asserts `identityVerified: true`** before token generation or member-table writes. The new PostgreSQL ledger CHECK constraints accept **only `delivery_method='email'`**, `reason_code='member_requested'`, and `delivery_status='pending'|'provider_accepted'|'failed'`. Redemption independently requires **`delivery_method='email'` AND `delivery_status='provider_accepted'`**; a fabricated legacy handoff row cannot authorize redemption. Adding a private method would require its own future Class A approval, DB migration and identity-verification design.
- Member receives link with a URL fragment (not HTTP query), which the new /member-recovery page removes from the address bar on first load. Token held in component state only. New password 12+ Unicode code points, <=72 UTF-8 bytes to avoid bcrypt truncation; password is hashed using the existing approved passwordUtils implementation.
- Redemption is **one database transaction**: claim locked token row, change only the token-bound member's password, revoke auth_sessions, record token redemption. If any step fails the entire transaction rolls back. Concurrent replays cannot both claim.
- Member's password never appears in admin response, logs or admin UI. The member must sign in again.

## Founder-controlled current-email re-verification (Class A beta draft)

**Founder instruction, source only:** Keep public signup and founder re-verification as separate authorization paths. The existing `/api/members/send-verification` continues to issue only to the database-stored address, checks an asserted address for mismatch, and rate-limits by IP and member. Its **email transport and sender are tightened** to explicitly configured managed SMTP and `SENDERS.noreply`. No Resend, capture provider, or unset selector is allowed; sender and accepted provider identity are verified. If acceptance is refused, the exact newly issued verification token is retired conditionally; provider acceptance still does **not** prove delivery. This touches existing registration mail, so compatibility verification is a release blocker.

The new default-OFF `POST /api/admin/members/recovery/verify-email` is founder-session-only; static shared admin password **cannot** authorize it. It requires exact Origin, a founder session revalidated with database locks, an explicit `confirmed: true` and a valid target member UUID. A request-supplied recipient address or other unrecognized field is refused. It re-reads the on-file email inside the transaction; never accepts operator-selected destinations. It applies IP/founder/member rate limits **plus a database-backed 10-minute resend cooldown**, and refuses accounts with no email or an already valid recovery email proof. It pins SMTP, uses `noreply@soullab.life`, and stores an ordinary 24-hour email-verification token only after validation. It never returns the bearer to the administrator. On confirmed SMTP acceptance it returns `provider_accepted`, never “delivered”; failures retire the exact issued token.

**Admin UX:** For an account with an email but no fresh current-address verification proof, show an explicit **Send verification email** action and a separate checkbox confirming that the member requested verification. The action does not change an existing password, mark email verified, create a recovery capability, or silently open private handoff. The member must click the one-time `/verify-email#token=...` email and confirm; then the founder reloads the Admin screen to verify updated eligibility. Only a subsequent, separately confirmed recovery issuance can send the password-reset link.

**Privacy/risk distinction:** The existing `members.email_verification_token` is presently stored in plaintext by the legacy email-verification system; this source correction does **not** silently migrate that flow to a digest-only token ledger. Password recovery tokens, by contrast, are SHA-256-digest-only in the new ledger. Existing generic signup verification is still reachable without a member session and remains bounded by its rate limit. This difference requires later explicit review, not a claim of complete identity-token custody parity.

## Hard separation / risks

1. **Schema deployment:** This PR includes a new PostgreSQL migration that also adds a member verification-proof column and a BEFORE UPDATE trigger. Merging it to canonical could cause the **next unrelated full production deploy to apply that migration automatically**, changing the verification lifecycle platform-wide. Require a separately founder-approved PostgreSQL migration/rollback and compatibility rehearsal; the feature flag does NOT disable the DB trigger. Production email verification for new and legacy members must be reconciled. Do not merge before verified backups and the release sequence are separately approved.
2. The legacy self-service /api/members/reset-password route still has plaintext tokens, non-atomic password-and-token updates, weak password minimum and raw email logging. It is **not repaired** by this member-admin flow. Replacing it is a different member-facing Class A scope; until reconciled, its risk remains.
3. [PR #1847](https://github.com/SoullabTech/Sovereign/pull/1847) handles POST admin-password audit and emergency reset-secret strengthening. No overlapping source files in this candidate. Neither draft authorizes merging the other.
4. [Issue #1848](https://github.com/SoullabTech/Sovereign/issues/1848) tracks the privileged terminal reset script. It remains executable and is **not affected** by this browser-based workflow.
5. The legacy Command Center UI treats a decorative local session marker as navigation access; real authority for Member Access is enforced server-side. A proper admin session experience may require separate product work; do not equate navigation access with verified founder status.
6. Origin validation is fixed to known production hosts and local development; test any alternate admin domain before release. Native iOS clients are not presumed compatible.
7. Email transport may be unavailable; isolated fictional SMTP responses cannot prove real delivery. **No manual link handoff is offered during the initial beta**, including when email is down, an address is unverified, or a member has no email. Do not bypass through the old password-reset script, direct SQL, shared admin secret, feature flag, or request-body spoofing. Future handoff/identity policy needs a separate authorization.
8. **Verification endpoint dependency:** `app/api/members/verify-email/route.ts` is modified to prevent an old token from verifying an address after a newer verification token or email change supersedes it. The missing `/verify-email` landing page is now implemented and requires a human confirmation click; new verification emails carry the token in a fragment, while legacy GET API links redirect to that page without consuming the token. The strict access matrix explicitly admits only the exact public verification page/API and the already rate-limited on-file email-verification issuer. It sets existing `members.email_verified_at`; the schema trigger then creates `recovery_email_verification_id`. This changes an **existing member authentication flow**, not merely the default-OFF recovery feature. Before any canonical merge, test ordinary verification routes against the exact restored production-shaped database and separately approve the coupled deploy and rollback ordering. The schema cannot be treated as a harmless optional feature-flag migration.
9. All requested changes are separate from JARVIS R7 and unrelated platform lanes. The protected 33-entry dirty worktree remains untouched.
