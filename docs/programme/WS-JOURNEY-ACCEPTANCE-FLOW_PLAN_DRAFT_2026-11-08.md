## 1. Principle
Develop around the writer's whole journey, not around more archetypes. One MAIA; capacities are stances the member declares
(never assigned). The unit of acceptance is a transition (reading → conversation, leave → return, refuse → remembered), not a feature.

| Role | Does | Never |

## 3. The loop (each journey passes through all stages; a stage that fails stops the loop)
1. **Observe** — the founder's or a tester's experience, verbatim, before any explanation.
2. **Trace** — real code path and stored data; attribute before repairing.
3. **Laws** — write observable pass/fail laws for the transition.
4. **Defeat candidates** — build the wrong designs; each must die on its named law (a surviving candidate repairs the suite).
5. **Build** — smallest reversible unit, additive, behind existing consent/Sanctuary law.
6. **Shadow witness** — real code against a disposable loopback database; fictional data; stubs named.
7. **Route/browser walk** — real route with a stubbed model transport, then a browser walk on fictional manuscripts.
8. **Independent review** — separate reviewer, adversarial.
9. **Founder walk** — the only evidence for experience claims. MAIA's behaviour is UNKNOWN until here.
10. **Release** — separate founder acts: merge, migration, deploy, production witness. Founder use is not witness.

Evidence classes are never merged: code-read < unit < shadow DB < route/browser < founder walk < production witness.

## 4. The seven journeys (proposed acceptance scenarios, none executed as a set yet)
1 first-time oral storyteller · 2 experienced manuscript author · 3 scholarly/technical professional · 4 memoirist ·
5 returning writer (read, close, ask later) · 6 writer who disagrees · 7 publishing author.
Each must also attack: stale passage, revoked access, lost response, changed passage mid-request, account switch, lost network.
