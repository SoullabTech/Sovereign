# F4.1 — TWO-RESOLVER SEPARATION

> **ADOPT.**

Writer's Studio shall keep two conceptually distinct resolution promises.

## A. Evidence resolver

Purpose:
> establish what MAIA actually read / what evidence supported the historical observation.

Law:

- resolves backward to exact historical evidence;
- is version-bound;
- uses existing digest / revision discipline;
- never performs fuzzy re-find;
- never guesses a new current locus;
- may report superseded / unavailable / historical-only;
- historical evidence is never overwritten by current text.

Existing `locateCurrent` / evidence semantics remain evidence-facing.

Do not weaken them to make member notes convenient.

## B. Member-place resolver

Purpose:
> help the member return to a place they themselves marked.

Law:

- may resolve forward toward the current Work;
- must disclose the resolution state;
- may never alter the historical creation address;
- may never silently guess;
- ambiguity stops rather than selects;
- current resolution and creation address remain distinct.

This resolver is a separate product contract.

### Consequence

Do not create one universal resolver with a "helpful" fallback.

The two promises have different epistemic duties.

# F4.3 — LAST PLACE / RETURNING WRITER

The prior `workContext.ts` ruling remains valid:

> a stored "last Work" must not become a second source of truth or a guessed default.

At the same time, Writer's Studio may support lawful re-entry inside a Work already selected by an authoritative context.

Therefore:

> **AUTHORIZE A MINIMAL PER-WORK RESUME STATE.**
>
> **DO NOT AUTHORIZE A GLOBAL "LAST WORK" SELECTOR.**

These are different things.

## Authorized resume semantics

Once a Work is lawfully selected through:
- explicit member choice;
- route/URL;
- existing Work context;
- another authoritative product selection;

Writer's Studio may persist, for that specific `(member, Work)`:

- last Studio mode;
- last stable chapter/section identity;
- optional meaningful durable place when supported;
- timestamp needed for truthful resume.

Purpose only:
> resume inside this Work.

## Explicitly forbidden

The resume object may NOT:

- decide which Work the member should open on cold start;
- override explicit URL / current Work selection;
- resurrect a Work the member no longer has access to;
- infer or store "what the member was struggling with";
- infer writing intent;
- persist every scroll/click;
- become an activity feed;
- serve as engagement telemetry;
- retain a narrative of behavior.

## Minimal retention shape

Conceptually:

```text
one current resume row per (member, Work)
overwritten rather than accumulated
deleted/cascaded with Work
```

Exact schema/name remains implementation-owned and requires its own migration authorization.

## Honest degradation

If no resume state exists:

> do not fabricate a "welcome back to where you left off" experience.

Open the Work through its normal authoritative context.
