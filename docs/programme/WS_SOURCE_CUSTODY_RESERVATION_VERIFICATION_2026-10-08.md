# Writer's Studio — durable source custody (local engineering verification)

**Status:** local implementation candidate, **RELEASE HOLD**. No production deploy, migration, push or merge. The existing source POST/PATCH guards intentionally remain HTTP 423. This packet is evidence of components, not certification of complete source saving.

## Candidate implementation

- `lib/workbench/sourceCustodyFiles.ts`: immutable, content-free filesystem intent journal (created and fsynced before content bytes), create-only staged originals, 50 MB per-file limit, and publish by directory rename. It refuses multiple, missing or zero-length canonical originals, malformed intent records, and unknown file names. Original bytes and directory entries are fsynced before publication. The intent journal remains until a caller independently proves the database's committed/aborted outcome; unresolved custody never triggers deletion or admission. A committed outcome requires exactly one nonempty published original. The only recovery API is not called by a live upload route.
- `database/migrations/20261008000002_source_custody_reservations.sql`: **unapplied migration candidate**. Creates `workbench_source_custody_ops` with a restrictive session FK, immutable reservation ownership, one-way state transitions and a per-session pending index. Its reservation trigger locks and checks the real authenticated `auth_sessions` record, current ordinary posture, expiry, revocation and member. Its privacy-transition trigger refuses acknowledgment while a reservation is `reserved`, `writing` or `recovering`. There is no time-based sweeping of member originals.
- `lib/workbench/sourceCustodyReservations.ts`: reserve under the auth-session row lock, commit the reservation before any upload data is accepted by the filesystem layer, then expose explicit writing/committed state helpers for the *same* database transaction client that will own the final `workbench_uploads` row. The successful source row must be member-owned, have a nonempty storage path and an eligible review/extraction status before the operation can be marked committed. **No route calls this candidate yet.**
- `scripts/verification/source-custody-reservation-local.cjs`: narrowly scoped to the *already existing* disposable database `sanctuary_protocol_verify_1008` with fixture rows created and removed for each run. It uses an additional disposable filesystem temporary directory, with only synthetic text.

## Test evidence

- `lib/workbench/__tests__/sourceCustodyFiles.test.ts`: 13/13 tests passed, including crash simulations at several stages, single-original custody, refusing incomplete committed originals, path validation, size limits, and cleanup after a proved abort.
- `lib/workbench/__tests__/sourceCustodyReservations.test.ts`: 6/6 tests passed, including absence of session credential, forged identity, missing session, reservation query rollback and use of the caller-supplied DB transaction client.
- Real PostgreSQL + filesystem verifier: **18/18 checks passed**, including contention in both orders, pending work preventing Sanctuary acknowledgment, a late reservation refusing after Sanctuary is acknowledged, revoked/expired/mismatched sessions refusing custody, and resuming from an on-disk journal to delete synthetic orphan bytes before acknowledging Sanctuary.
- The SQL migration candidate was **executed only on the disposable verification DB**, not on production or the shared `maia_consciousness_test` database.

## Remaining release blockers — non-negotiable

1. **Old-version writer.** The reported production commit `c9e4f7f7e` invokes the legacy intake/patch writers without a source-session reservation. The proposed schema alone does NOT prevent that old writer from persisting bytes during Sanctuary. Before any schema cutover, a separately verified server/edge write fence must protect those old routes while the old application is still serving. The ordered-prefix compatibility review must include this behavior explicitly.
2. **Full intake integration.** `ingestWorkbenchUpload` still inserts and updates with independent pooled `query()` calls and writes directly to the canonical filesystem directory. It has NOT been converted to the new reservation, same-transaction client, staged extraction and DB acknowledgment sequence. Source POST/PATCH remain held. The reviewed-text edit lifecycle needs its own crash journal and same exclusion law.
3. **Recovery ownership.** The local verifier simulates process death by discarding in-memory writer state. A live janitor must never race an active worker: it requires durable ownership/CAS or a governed writer-quiescence proof before claiming stale reservations. If cleanup fails, the reservation must remain nonterminal and privacy transition must remain refused. Neither TTL alone nor a missing session row permits deletion.
4. **DB/filesystem atomics and error handling.** A filesystem rename is not a PostgreSQL commit. The new source flow must fsync, publish, finalize the source row and reservation in one leased DB transaction, and preserve the intent journal until a database-verified outcome. For OCR errors where an original was deliberately admitted, preserve it; never "fix" a partial extraction by deleting the only lawful original.
5. **Migration compatibility.** The pending candidate history now includes THREE migration files: the chapter-overview lens, source-session posture, and new reservation ledger. Current production ledger, exact old/new readers, each committed prefix and rollback/fencing limitations still need an admitted review-custody evidence packet. No migration was run on production. The committed source-posture migration and the newly proposed reservation migration were exercised only in an isolated disposable database.
6. **Authenticated positive walkthrough.** The earlier Chrome witness proved the Materials UI, beta access, and HTTP 423 without DB writes. It did NOT prove positive Bring → Keep → Explore → Place; that awaits the complete reviewed intake and migration-safe test environment.
7. **Global broad typecheck.** The prior `npm run typecheck` was still blocked by a Stripe API-version mismatch in `lib/stripe/config.ts` that exists at the old target commit; do not absorb it into the baseline or treat passing focused tests as broad build approval.

**Disposition: NO-GO.** Preserve the upload hold until the above conditions are actually demonstrated, not merely specified.
