R5A establishes the first prerequisite required by R4: an immutable, independently verifiable binding between a persisted route record and the Work Unit that owns it.

R5A does not authorize or connect provider execution.

## 1. Binding shape

For newly created route-bound Work Units, MAIN deterministically computes and persists:

- route_record
- route_digest
- route_version
- source
- bound_at_sha
- execution_connected = false

The digest is:

- SHA-256
- computed from the exact canonicalized route record
- generated by the same routeDigest() law used by R4
- never supplied by the renderer

The persisted source remains:

R2-pure-router
## 2. MAIN owns the binding

The renderer may submit structured routing intent only.

It may not submit:

- route_record
- route_digest
- route_version
- canonical SHA
- route source
- authority envelope

MAIN:

1. constructs structured route input;
2. invokes the pure R2 router;
3. computes the R4-compatible digest of that exact route;
4. obtains the current repository SHA;
5. passes those immutable facts into Work Unit packet authoring.

The packet authoring module refuses a routed Work Unit when the MAIN-computed digest is absent or malformed.

## 3. Immutability after creation

R5A preserves the canonical Work Unit creation seam:

- packet creation is create-once;
- existing Work Unit IDs are not overwritten;
- a second create attempt with the same Work Unit ID is refused as WORK_UNIT_ID_IN_USE;
- the existing packet bytes remain unchanged after refused rebinding.

R5A does not introduce an update-in-place path for route bindings.

There is no route rebinding operation.

If a materially different route is required, it must occur through a separately governed successor act rather than rewriting the original packet.
## 4. Integrity law

R4 admission now validates both the route record and the persisted binding metadata.

The binding fails closed when any of these occur:

- route_digest missing;
- route_digest does not match route_record;
- route_version sibling does not match route_record.route_version;
- route_record version is not the ratified version;
- source is not R2-pure-router;
- bound_at_sha differs from the current Work Unit canonical SHA;
- route carries granted authority;
- execution is already connected out of order.

The new typed metadata blocker is:

ROUTE_BINDING_VERSION_MISMATCH

Existing R4 blockers remain authoritative, including:

- ROUTE_DIGEST_REQUIRED
- ROUTE_DIGEST_MISMATCH
- ROUTE_SHA_STALE
- ROUTE_VERSION_MISMATCH
- ROUTE_SOURCE_MISMATCH
- ROUTE_AUTHORITY_TAMPER
- EXECUTION_PRECONNECTED

## 5. No authority creation

A valid immutable binding establishes integrity only.

It adds no:

- provider.execute:* authority;
- network.external authority;
- provider.spend authority;
- repository disclosure;
- repository write authority;
- merge authority;
- deploy authority;
- production authority;
- constitutional authority;
- Founder authority.
A newly bound Work Unit still carries:

authorized_acts = [repo.read]

and:

provider_strategy = []
execution_connected = false

Therefore a newly bound local route can pass R4 integrity checks while still returning:

HELD_FOR_AUTHORITY

until a separately governed human execution authorization exists.

## 6. No migration or backfill

R5A applies to newly created route-bound Work Units after R5A integration.

It does not rewrite existing R3 Work Units.

Historical R3 packets that lack route_digest remain truthful historical artifacts and continue to fail R4 admission with ROUTE_DIGEST_REQUIRED.

No migration is authorized or required by R5A.

## 8. Execution boundary

R5A does not modify the route-bound run-provider guard.

A route-bound Work Unit remains non-executable through the existing Desktop provider path.

R5A does not:

- call Qwen;
- call GPT-OSS;
- call Inkling;
- call Nemotron;
- inspect credentials or Keychain;
- access the network;
- spend provider funds;
- grant provider execution authority;
- connect R4 admission to run-provider;
- deploy;
- mutate production.
