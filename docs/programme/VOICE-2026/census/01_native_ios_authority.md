# VOICE-2026 · CENSUS-01 — Native iOS Audio Authority (executable, not intended)

**Lane:** VOICE-2026 / CENSUS-01 · **Branch read:** `claude/voice-2026-census-01` (HEAD `e1c6f527b`) · **Date:** 2026-09-11 · **Mode:** READ-ONLY source census. No source file was modified.

**Question answered:** on the `/maia` screen of the iOS Capacitor app, which native code can *actually execute* against AVAudioSession, AVAudioEngine, SFSpeechRecognizer, the microphone, and WKWebView media behaviour — and from which JavaScript call sites.

**Method:** every `.swift`/`.m`/`.plist`/storyboard under `ios/App/App`, the two native plugins that touch audio (`@capacitor-community/speech-recognition@7.0.1` as patched by `patches/@capacitor-community+speech-recognition+7.0.1.patch`, `capacitor-voice-recorder@7.0.6`), the Capacitor 8.0.2 bridge registration path and WKWebView configuration, and a grep of every `AVAudioSession` / interruption / route / synthesizer symbol across `ios/` and all `node_modules/@capacitor*`, `capacitor-*`, `@southdevs/*` iOS sources. JS reachability was traced by import graph from `app/maia/page.tsx` → `components/OracleConversation.tsx` → `components/voice/ContinuousConversation.tsx` / `components/ui/ModernTextInput.tsx`.

Legend for the reachability column — **YES** = compiled, registered with the bridge, and invoked from code on the `/maia` import graph · **NO** = not on the `/maia` graph (dead, test-only, or excluded from the iOS build) · **UNREGISTERED** = compiled into the binary but never registered with the Capacitor bridge, so every JS call to it rejects · **NOT COMPILED** = source file exists but is not in the Xcode target.

## 2. Authority findings

### 2.1 Who owns AVAudioSession on the live `/maia` iOS path today

**Exactly one executable owner: the patched `@capacitor-community/speech-recognition` plugin, and only inside `start()`.** `Plugin.swift:79-96` is the sole reachable code that sets category, mode, options, preferred sample rate, IO buffer duration, or activates the session. It executes on every `NativeSpeechRecognition.start()` (`ContinuousConversation.tsx:3306`), i.e. on every hands-free restart, with the same values each time:

| Set | Where | Value |
|---|---|---|
| category / mode / options | `Plugin.swift:82-86` | `.playAndRecord` · `.voiceChat` · `[.defaultToSpeaker, .allowBluetooth, .allowBluetoothA2DP, .mixWithOthers]` |
| preferred sample rate | `Plugin.swift:87` | `48000` |
| preferred IO buffer duration | `Plugin.swift:88` | `0.01` |
| active | `Plugin.swift:89` | `setActive(true, options: .notifyOthersOnDeactivation)` |

**Nothing reachable ever deactivates the session** (#4). Once the first `start()` has run, the session stays in the state above until the process ends, modulo whatever WebKit's content process or the OS does — which is outside this source (§4).

Everything else that *could* set the session is either unregistered (`AudioSessionManager`, #13–#16: `.playAndRecord/.measurement/[.defaultToSpeaker,.allowBluetooth,.duckOthers]`, `.playback/.spokenAudio/[.duckOthers]`, `setActive(false, .notifyOthersOnDeactivation)`), not compiled (`VoiceController`), or fails-closed upstream in JS (`VoiceRecorder`, #21–#22: `.playAndRecord` with default mode and no options, `setActive(true)`, later `setActive(false)` + category restore).

**Before the first `start()`** the category is not set by any MAIA code; `AppDelegate.swift:9-13` does nothing. What WebKit's media stack does to the session in the app process when Web Audio starts rendering is not determinable from this source (§4, Q1).

### 2.2 Interruption / route-change handling

There are **no native observers** of `AVAudioSession.interruptionNotification`, `routeChangeNotification`, or `mediaServicesWereResetNotification` anywhere in the app target or any bundled plugin (#27). Nothing native reacts to a phone call, Siri, a Bluetooth route change, or a media-services reset. The plugin's task callback (#9) is the only native code that reacts to *anything* asynchronous, and it reacts only to what Speech framework delivers to the task.

What the web calls "iOS interruption" is app lifecycle only: `OracleConversation.tsx:4417-4437` subscribes to `@capacitor/app` `appStateChange` and forwards to `ContinuousConversation`'s `onInterruptionStart` / `onInterruptionEnd` (`:3948-3958`, `:4042-4056`), each of which calls `NativeSpeechRecognition.stop()` (#7). An actual AVAudioSession interruption that does not background the app reaches no handler.

### 2.4 Conflicts between owners (source-level)

1. **Speech plugin vs itself — task identity.** `stop()` (#7) ends audio but leaves the task alive and un-cancelled, and leaves `self.audioEngine` non-nil. The next `start()` first runs `cleanup()` (`:67`), which cancels that task, then creates a **new** engine (`:99`) and a **new** task (`:135`). The old task's terminal callback (cancellation error, or a late final after `endAudio()`) executes `self.audioEngine?.stop()` (`:163`) against whichever engine is current at delivery time, because the closure carries no task identity. **Source establishes the mechanism; whether delivery lands after `:99`/`:201` on a given run is timing and cannot be settled from source** (inference marked). This is the code-consistent form of hypothesis E16.5.
2. **Speech plugin vs itself — double `stopped` event.** `stop()` emits `listeningState:stopped` (`:237`), and the task callback emits it again when the ended request finalises or errors (`:167`). The live `listeningState` handler (`ContinuousConversation.tsx:3058-3110`) treats every `stopped` as a restart opportunity when `wantsToListen` (`:3096`). Two emissions per stop are a source fact; that they produce two restart evaluations is an inference from the handler having no de-duplication visible at `:3058-3110`.
3. **Gatekeeper vs speech plugin (latent, not active on this branch).** `AudioSessionManager.performFullTeardown()` (`:239-274`) can only cancel/stop objects the gatekeeper itself created (`:35-38`); it has no reference to the community plugin's engine or task. So if registered, `prepareForSpeaking` would run `setActive(false)` → `.playback` → `setActive(true)` **underneath a possibly still-running community engine**, with no coordination. On the live path the two triggers are independent: `OracleConversation.tsx:2004` (before TTS fetch) and `ContinuousConversation.tsx:1991` (fire-and-forget IIFE in reaction to the speaking state). Their relative order is not fixed by source. This is Invariant 3.1's "two owners" as it exists in code — inert today only because #14 rejects.

## 3. Registration status of in-app plugins on this branch

**Mechanism (Capacitor 8.0.2):** `CapacitorBridge.registerPlugins()` (`node_modules/@capacitor/ios/Capacitor/Capacitor/CapacitorBridge.swift:304-333`) registers five core plugins plus every class named in the **bundled** `capacitor.config.json` → `packageClassList` (`:307-326`, `RegistrationList` at `:9-11`), resolved with `NSClassFromString`. That JSON is generated by the CLI on every `cap copy`/`cap sync` (`scripts/build-ios.sh:186` runs `npx cap sync ios`): `tasks/copy.js:79` copies `capacitor.config.ts` → JSON, then `:83` calls `generateIOSPackageJSON`, whose `writePluginJSON` **overwrites** `packageClassList` with the classes found by scanning **npm plugin** `.swift`/`.m` files for `@objc(Name)` / `CAP_PLUGIN(Name` (`util/iosplugin.js:9-24, 32-50, 50-54`). The generated file is gitignored (`ios/.gitignore:12`), so the values `capacitor.config.ts:39-55` declares (`'AudioSessionManager'`, `'VoiceController'`) are **overwritten before they reach the bundle**.
