## 0. Why this lane exists

The `IOS-CONVERSATION-RUNTIME-01` lane witnessed, on device with the
debugger attached (E16–E18):

- a long-utterance drop caused by a recognizer re-segmenting inside one
  task with no stop event, the web layer replacing its buffer with each
  partial (537 chars discarded, ~60 submitted);
- a post-TTS re-entry storm: at least four independent restart drivers,
  each pre-emptively stopping the previous engine, 37 recognizer
  generations in ≈46 s, the audio-session route configuration strictly
  alternating between two shapes, ended only by an inactivity guard
  standing the microphone down with no self-recovery;
- after the storm, an engine reporting `running` while its input tap
  delivered denormal-zero levels (8.8e-43) — *an active engine on a dead
  microphone*;
- MAIA inaudible on 3/3 replies of the repaired build while the web
  layer's `Audio output confirmed` line reported graph activity.

Founder reading (E21): this is not "a few voice bugs". Two years of
incremental growth — browser capture, recognizer lifecycle, native audio
management, TTS, turn timers, WebView state, and protections added around
each — produced a system in which recognition, audio hardware,
turn-taking, playback and UI state are entangled. The 37 restarts are the
picture: **components successfully doing what they think they own while
the conversation as a whole collapses.** Multiple concepts negotiating
custody of one physical organism.

Defect-driven development on that runtime **closes** after two final
acts (E19 historical A/B; E20 Repair Two witness). From then on the
existing runtime is a **legacy reference implementation and evidence
source**. Anything further it exposes is recorded, not repaired.

## 1. The question

The old programme asked: *why didn't the microphone come back?*

This lane asks:

> **What is the smallest coherent organism capable of hearing, speaking,
> remaining present, surviving interruption, and carrying an
> uninterrupted human turn — and how should canonical MAIA connect to
> it?**

## 2. Scope and non-scope

**In scope:** the sensory/motor substrate — capture, playback, audio
session ownership, turn-taking, interruption recovery, routing, the
WebView ⇄ native boundary, and the health model that says whether the
organism is alive.

**Out of scope, explicitly:** MAIA cognition. *We are not redesigning
MAIA cognition. We are designing a new sensory/motor system around it.*
The Deep-Intelligence Gate holds unchanged: spoken and typed turns
converge before cognition begins; voice may have a different capture
path, never a different mind. Sovereignty holds unchanged: STT and TTS
remain pluggable, local-or-on-device, never a cloud AI provider.

## 3. Central architectural shift (founder, E21 — proposed, not ratified)

**Voice is not STT + TTS. Voice is a persistent conversational audio
runtime.**

```text
human sound
    ↓
persistent conversational audio runtime
    ↓
speech / turn events
    ↓
canonical MAIA
    ↓
response stream
    ↓
persistent conversational audio runtime
    ↓
MAIA sound
```

Target shape, approximately:

```text
                    MAIA
             canonical cognition
                      │
               text / events
                      │
                      ▼
          ┌─────────────────────┐
          │ ConversationRuntime │
          │     (native actor)  │
          └──────────┬──────────┘
                     │
      ┌──────────────┼────────────────┐
      │              │                │
      ▼              ▼                ▼
 TurnManager     STT Adapter       TTS Adapter
      │              │                │
      └──────────────┼────────────────┘
                     │
                     ▼
             ┌───────────────┐
             │ Native Audio  │
             │   Authority   │
             └───────┬───────┘
                     │
             AVAudioSession
                     │
             Voice Processing I/O
                     │
              mic ⇄ speaker
```

Principles carried from the ruling:

- **One thing owns the hardware.** A native `ConversationRuntime` owns
  the conversational session. Nothing else sets `AVAudioSession`
  category, mode, activation, route, microphone lifecycle or output
  lifecycle. STT does not own the mic; TTS does not own the speaker; the
  WebView does not own the mic; the turn detector does not own the mic.
  They consume or produce streams.
- **The audio session lives for the conversation.** Enter conversation →
  one session (`playAndRecord` / `voiceChat` / voice processing) → listen
  · think · speak · listen … → leave conversation. Logical turn-taking
  does not require physical hardware reconfiguration. Half-duplex
  behaviour may remain initially; true barge-in becomes an evolution,
  not another architecture replacement.
- **Turn-taking is its own intelligence.** A recognition segment is not a
  human turn. A separate `TurnManager` decides: speech began · continued
  · paused · utterance probably complete · utterance committed · MAIA
  thinking · MAIA speaking · member interrupted. Therefore: recognizer
  restart ≠ turn end · recognizer finalization ≠ turn end · silence
  timeout ≠ necessarily turn end · audio-engine restart ≠ turn end.
  (Repair Two, E20, becomes a constitutional principle here rather than
  a patch. Its re-arm-on-recognition-start is explicitly NOT carried
  forward: in the new runtime, recognition starting or restarting has no
  authority over whether a human turn remains alive.)
- **The WebView becomes a client of voice.** On iOS the web application
  does not operate the microphone. It says `startConversation()` ·
  `stopConversation()` · `mute()` · `interrupt()` and receives
  `voice.state` · `voice.level` · `transcript.partial` ·
  `transcript.final` · `turn.committed` · `maia.speaking` ·
  `maia.finished` · `route.changed` · `voice.interrupted` ·
  `voice.recovered`. Native audio is authoritative; the UI remains web;
  MAIA remains MAIA.
- **Sovereignty is preserved by protocol.** `SpeechRecognizer` and
  `SpeechSynthesizer` protocols with MAIA-sovereign, native, and future
  engines behind them. What is borrowed from contemporary platform
  designs is the separation of capture from analysis, not the engine.

Founder-cited platform references (NOT verified in-session; the survey
act verifies or marks them): Apple `AVAudioSession` `.playAndRecord`
category and `.voiceChat` mode for two-way voice, continued playback with
the Ring/Silent switch engaged under `.playAndRecord`; `AVAudioIONode`
`setVoiceProcessingEnabled(_:)` / Voice I/O audio unit for AGC and
duplex processing at the audio layer; `SpeechAnalyzer` separating input,
analysis and results with provisional and finalized results represented
independently; `WKWebView` having its own microphone capture state.

## 4. Draft invariants (founder-proposed, E21 — CANDIDATE, not ratified)

| ID | Name | Statement |
|---|---|---|
| VOICE-01 | One hardware sovereign | Exactly one component owns `AVAudioSession` and physical I/O. |
| VOICE-02 | Conversation lifetime ≠ recognition lifetime | Recognizer creation, finalization, failure or restart cannot open or close the physical conversation session. |
| VOICE-03 | Segment ≠ turn | A recognizer segment boundary has no authority to discard or commit the human's utterance. |
| VOICE-04 | Speaking and listening share one session | MAIA output does not require replacing the audio configuration used for human input. |
| VOICE-05 | Web has no iOS hardware authority | The WebView expresses intention; the native runtime controls audio. |
| VOICE-06 | Recovery belongs to the runtime | A recognition engine can die and restart without the microphone changing ownership. |
| VOICE-07 | Observable truth | At any moment there is one authoritative answer to: session active? · input alive? · output alive? · route? · input level? · MAIA speaking? · human speaking? · recognizer alive? · current turn? |
| VOICE-08 | Silence is measurable | An engine claiming `running=true` while receiving digital zero is not healthy. The E18 condition is an invariant violation, not something discovered 69 s later. |

**First principle (from E18):** *a subsystem may report itself healthy
while the organism is dead.* Health is therefore never defined through
component state alone. The runtime needs end-to-end **physiological**
invariants: actual input energy · actual rendered output · stable route
· coherent session ownership · active turn continuity · recovery
without human intervention.

These are candidates. Ratification is a founder act after the census and
survey have tested them against the executable system and the platform.

## 6. CENSUS-01 — definition

**Read-only.** Find every thing in the codebase that can currently:

```text
request microphone access
open microphone capture
start an audio engine
stop an audio engine

set AVAudioSession category
set AVAudioSession mode
set AVAudioSession active

change output route
play synthesized audio

start recognition
stop recognition
restart recognition

declare speech complete
close a turn
start a timer
stand down listening

change mic UI state
change conversation state
```

For each: **who can start it, stop it, restart it, and change its
configuration**, under what trigger, and whether it is reachable on the
live `/maia` path on iOS. Then draw the **actual** authority graph —
*the executable architecture, not the intended one.*

Method: five parallel read-only sweeps (native iOS authority · live web
capture/recognition lifecycle · TTS/playback/output · turn closure and
conversation/UI state · other capture paths and reachability), each
citing `file:line`, each recording open questions rather than guessing;
then one assembled census with the authority graph and findings.
Nothing in the census is a repair proposal.

  accepted by founder act.
- No claim that Voice 2026 "works" ahead of KERNEL-01's predeclared

## 8. The five-year direction this substrate serves (founder, E21 — VISION)

natural multi-turn conversation → streaming responses → barge-in → MAIA
can hear while speaking → prosodic awareness → pace / silence / breath →
affective acoustic signals → relational timing → embodied conversational
presence. A traditional assistant thinks *audio → text → answer → audio*;
what MAIA needs is *presence → listening → relation → response →
continued presence*. The engineering architecture should finally reflect
that. (Claim state: VISION. Nothing here is live or designed yet.)

## 9. CENSUS-01 assembly rules (founder, 2026-09-11)

Six good sweeps must not become six disconnected reports. The assembled
census resolves every finding into ONE schema:

| Domain | Current owner | Can start | Can stop | Can restart | Can reconfigure | Observed conflicts | Future disposition |
|---|---|---|---|---|---|---|---|
| AVAudioSession | | | | | | | keep / retire / isolate |
| microphone capture | | | | | | | |
| recognizer | | | | | | | |
| turn closure | | | | | | | |
| TTS / output | | | | | | | |
| routing | | | | | | | |
| interruption recovery | | | | | | | |
| WebView media | | | | | | | |
| UI state | | | | | | | |

From that table, three derivations — in this order:

1. **The actual authority graph.** Not component architecture —
   *authority*: who can cause physical audio state to change? who can
   terminate another subsystem's work? who can decide a human turn is
   finished? who can declare recovery? Any node with overlapping
   authority is immediately interesting.
2. **The failure graph.** Overlay E16 / E18 / E19 / E20 onto the census:
   event → owner A acts → owner B reacts → configuration changes →
   recognizer restarts → turn state changes → input/output becomes
   unhealthy. The aim is to explain the restart storm as a
   *deterministic interaction*, not a collection of bugs.
3. **The 2026 disposition.** Every significant old subsystem gets exactly
   one of four labels — **KEEP** (concept and implementation survive) ·
   **ADAPT** (concept survives, implementation changes) · **REPLACE**
   (responsibility survives, owner changes) · **REMOVE** (responsibility
   should no longer exist). This prevents the new architecture from
   becoming "old voice, reorganized".

**Survey rule:** separate *platform capability* from *architectural
recommendation*. "Apple can do X", "Capacitor supports Y", "modern
realtime systems use Z" are evidence. They do not automatically become
MAIA's design.

**The synthesis question** — the next substantive act after the sweeps
land, and not another repair:

> Given MAIA's sovereignty, relational continuity, mobile requirements,
> and future barge-in / prosodic ambitions, what is the smallest lawful
> voice organism we should own?
