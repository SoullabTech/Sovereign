**Umbrella programme charter · ratified in principle 2026-09-03 (founder) · docs-only**

**Bound to canonical:** `clean-main-no-secrets @ 6d093fb3a41491682d2ee96353f394397f286a8f`

This charter is the umbrella under which CMT-01 (canonical turn construction), MIPA Phase 0 (P1–P6), retrieval, model-serving behaviour, explicit recollection, developmental memory, relationship memory, symbolic memory, and every future memory capability are worked. None of those subsystems is the goal. It is not a CMT spec, not a memory-subsystem design, and not a witness record; those live where they already live (`docs/architecture/MAIA_CANONICAL_TURN_ARCHITECTURE_SPEC_v0.1.md`, `docs/specs/MIPA_PHASE_0_SOVEREIGNTY_PREREQUISITES_SPEC.md`, `docs/architecture/REFUSAL_REGISTRY.md`).

> **Headline law: Maximize useful continuity under member authority.** Not: minimize memory exposure. Those are different architectures.
>
> **The member-facing objective is not memory minimization. It is rich, accurate and increasingly comprehensive continuity. Governance exists so that more memory can safely become usable, not so that the system can congratulate itself for remembering less.**
>
> **A protection that unnecessarily prevents relevant member-owned memory from participating is itself a memory defect.**
>
> **The manifest is diagnostic evidence. Member-experienced continuity is completion.**

## 1. Purpose

Make the full MAIA/Jarvis memory organism operational end-to-end for everything that already exists, put it in beta members' hands, observe lived use, refine from what members actually experience — and then deliberately build the memory classes that do not yet exist.

The destination: a MAIA who genuinely knows the person over time — their conversations, experiences, symbols, changes, relationships, questions, decisions and history — and can bring that knowing into the present naturally, without confusing possession of memory with authority over the person.

Members are asking for the opposite of minimization. They want MAIA to remember more of their life, more accurately, across more time, and to use it naturally when it matters. Sovereignty determines *how* memory participates. It is not the reason for shrinking it.

The desired direction:

```text
MORE remembered · MORE retrievable · MORE connected across time
MORE available when relevant · MORE intelligently used

while also being

accurately attributed · member-governed · contextually appropriate
correctable · retractable · non-coercive
```

## 2. Anti-drift rule

**CMT/MIPA exists to make Jarvis memory trustworthy and usable. It is an accelerator for the memory organism, not a brake, and not the destination.**

The canonical turn boundary answers: *"Of everything MAIA knows about this member, what is relevant and lawful to bring into this turn?"* It does not default to *"How much can we keep out?"* A `HELD` or `EXCLUDED` memory requires a real, named reason. "We are being cautious" is not one. For member-authored memory with valid provenance and no active restriction, the bias is availability and intelligent use.

Drifts this rule refuses, each observed in the last week:

1. **Architecture as completion.** A green manifest, a certified gate, or a passing suite is diagnostic evidence about one link of the chain. It is never "memory works."
2. **"Memory failed" as a diagnosis.** A miss is located at one link of the chain (§3) and repaired there. Today's I Ching miss sat at *use* with every retrieval layer up; "memory failed" would have sent the repair to the wrong place.
3. **Subsystem for organism.** Building or witnessing one memory subsystem is not the programme. The programme is the member no longer having to re-explain their life.
4. **The exquisitely governed amnesiac.** A system can be perfectly "safe" and deeply frustrating if every meaningful memory sits behind a gate. **False-negative memory is a first-class defect** (§3, §7). We do not establish a mediocre-memory baseline and then spend months carefully preserving it.

**Beta memory doctrine — continuity-first, member-governed.** For members who opt into the MAIA beta, relevant member memory is available to MAIA by default unless there is a specific reason it should not participate. Restrictions are exceptions, not the product:

```text
member chose continuity
   ↓
memory exists and is attributable
   ↓
available to MAIA by default
   ↓
specific restrictions can narrow it
   ↓
MAIA learns to use it well
```

The beta posture is: build toward the richest continuity we can responsibly make available, put it in members' hands, observe what happens, refine from lived use. Precision is added where actual members show it is needed, not in advance.

**"Ask forgiveness later" is bounded.** It is the right posture for rough UX, imperfect relevance, an awkward resurfacing, or MAIA remembering something the member did not expect and then learning from the reaction. It does not apply to hidden disclosure, third-party information, Sanctuary material, or silently inventing consent. Those are a different class of mistake and are held in §10.

## 3. Governing diagnostic chain

Every memory layer is judged on one chain, in order. A break is named at the first link that fails and repaired there.

```text
REMEMBERED
  → the material is stored, durable, and attributable to a source
RETRIEVABLE
  → a loader can return it for this member at this turn
AVAILABLE BY DEFAULT WHEN LAWFUL
  → nothing withholds it except a specific, named restriction
    (sealed, Sanctuary, retracted, third-party without authority, unendorsed inference)
RELEVANTLY ADMITTED
  → the turn boundary admits what is relevant to this turn and records why
INTELLIGENTLY USED
  → MAIA brings the right thing forward at the right moment
EXPERIENCED AS CONTINUITY
  → the member does not have to explain their life again
```

Two diagnostic questions are asked of every witnessed turn, and both are defects:

```text
FALSE POSITIVE   MAIA brought forward memory that should not have participated.
FALSE NEGATIVE   MAIA possessed relevant memory and failed to bring it forward.
```

For the beta, some false positives are tolerated while relevance is learned, provided they are transparent, reversible, and not privacy violations; the member gets an easy "don't use that again." Repeated false negatives — "we've talked about this six times, why don't you know me?" — are the trust failure this programme exists to eliminate.

Properties of the chain: each link is witnessed separately and can fail separately; only the constructed turn can witness AVAILABLE and ADMITTED per turn (its manifest attests what was admitted, held, excluded and why); USED and EXPERIENCED are observed in the conversation.

## 7. Production acceptance protocol

For any layer to be declared `LIVE + FUNCTIONAL`, all six links must be witnessed on real member turns in production, and both defect classes scored:

```text
Can MAIA find it?                      REMEMBERED / RETRIEVABLE   loader log / manifest returned > 0
Is it available to her by default?     AVAILABLE                  no withholding without a named restriction
Did the turn admit what was relevant?  ADMITTED                   manifest: admitted / held / excluded, with reason
Did she use it well?                   USED                       the response draws on it (operator-judged, probe-controlled)
Does the member experience continuity? EXPERIENCED                the member says so, unprompted

FALSE POSITIVE   brought forward what should not have participated
FALSE NEGATIVE   possessed relevant memory and did not bring it forward
```

Protocol rules, all learned this week:

- **Open → create real traffic → collect → close.** A witness window with no operator turns is empty, not a reading. Incidental traffic on this server is unreliable.
- **Provenance and executable instrument must name the same candidate** before any window opens: `GIT_COMMIT` in the running container, the instrument's source present in the image, the marker compiled into the route.
- **Collect before close.** A lane recreate discards the container's logs.
- **Counters must be real instruments.** `docker logs maia-caddy` is not an access log (the `soullab.life` block logs to `/var/log/caddy/access.log`, lost on caddy recreate). Use the file, or `agent_runs.origin_route`.
- **The USED probe is controlled.** It must require a concrete detail from the earlier session that has not been restated in the current conversation; otherwise MAIA can appear to remember by using what she was just told.
- **Session-resumption is a design rule, not a break.** Prior-exchange recall is withheld when the previous session ended < 30 min ago and the current session has < 3 turns (`lib/maia/conversationalRecallBlock.ts:76–102`). Probe from turn 3 onward. *Pass 2 question: is this rule itself a false-negative source for members who open a new conversation to continue?*
- **Classify each turn separately** under: session-resumption suppression (expected) · recognized identity + `returned: 0` (retrieval/scope) · `anon-or-unrecognized` (identity) · material surfaced but detail missed (USED) · no retained marker (indeterminate, not PASS or FAIL) · and FP/FN.
- **No repair under the authority to witness.** A finding is captured; the repair is its own act. In the beta, that act can be fast.

## 8. Dependency on canonical turn construction

AVAILABLE and ADMITTED are properties of the turn-construction boundary. They cannot be witnessed by reading loaders or by reading the conversation. Only a manifest emitted by the constructor that actually built the turn attests, per turn, what was admitted, held, excluded, and why — and it is also the instrument for the false-negative census (admitted but unused; available but not admitted).

> **Tracks A1–A2 — census and classification — may proceed while the turn boundary is being stabilized. Track A3 — end-to-end production proof of lawful participation — requires one canonical turn-construction boundary. No memory layer may be declared fully operational from production evidence taken against a moving or competing participation boundary.**

As of the binding SHA there are two competing implementations for `/list`:

- **Path B** (`lib/maia/turn/*`; deploy candidate `3e31bc0ff…`; adjudicated to stand 2026-09-03; carries MIPA Phase 0 in full) — **not in canonical**.
- **`lib/maia/canonical-turn/*`** (M0–M2 / pdc-1 contract; shadow on by default via `MAIA_CANONICAL_SHADOW !== '0'`) — **in canonical `6d093fb3a`**, deployed, running.

Neither contains the other. `3e31bc0` merges onto `6d093fb3a` without conflict, so a reconciled candidate is mechanically available, but two `/list` shadows cannot coexist in one route without a reconciliation decision. The record of how two boundaries came to alternate in production is in the CMT spec §12a.

**What this dependency does not block.** Pass 1 wiring of stores that already exist (divination, anchors, member-authored material, significant moments on `/list`) and Pass 2 member observation do not require the boundary decision, provided they are made in **one** lineage so that a third fork is not created.
