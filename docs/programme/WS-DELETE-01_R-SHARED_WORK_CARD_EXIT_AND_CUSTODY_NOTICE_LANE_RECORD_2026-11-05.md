## 5. Diagnosis of the production 500 (from the code; production itself was not read)

The founder's second screenshot shows DELETE 500 followed at once by GET living-works and GET manuscripts. In the old controller a refresh followed only the `removed:true` answer, so that 500 was
`{removed:true, refusal:'custody_incomplete'}`: **the rows were gone and custody was not confirmed.** The repository says which conditions produce that answer (`sweptAll` is false when the deletion's
own queued bytes are not destroyed OR the R20 recovery seal could not be written):

| Mode | Cause | Operator signature (container log) | Note |
|---|---|---|---|
| R1 | The R20 ledger is not configured. `sealR20DeletionLedger()` throws unless `R20_LEDGER_FILE`, `R20_HIGH_WATER_FILE` and `R20_LEDGER_KEY_FILE` are set to absolute paths (`lib/recovery/r20DeletionLedger.ts:264-266`), and, once set, unless the key file EXISTS and holds 32 bytes (raw, 64 hex characters or base64; otherwise `R20_LEDGER_KEY_UNAVAILABLE` / `R20_LEDGER_KEY_INVALID`) and the ledger and high-water files exist or `R20_LEDGER_ALLOW_INITIALIZE=true` | `[MAIA/press] R20 recovery seal still owed { code: R20_LEDGER_FILE_MISSING }` (or `…HIGH_WATER…`, `…KEY_FILE_MISSING`, `…KEY_UNAVAILABLE`, `…KEY_INVALID`) | **The most likely.** The pending-deploy inventory (L3) already found the three names in no tracked compose or env template. In this mode EVERY delete ends in the alert; the body says `unconfirmed:{deletionRecord:true}` and the member is told only that. **Superseded 2026-11-06, see 6.9.2:** the read-only readout found no `R20_*` variable on the running app container, so this is the configuration in production; that is consistent with the original 500, not proof of it. |
| R2 | This deletion's own original-file bytes could not be destroyed (permissions, read-only mount, a symlinked or hard-linked path the vault refuses) | `[MAIA/press] vault erasure still owed (errno=EACCES)` with `artifactsQueued: N`, no `R20 recovery seal still owed` line | Only for a writing that had an original file. The body says `unconfirmed:{originalFile:true}` (probe SB-1) |
| R3 | **Before this review only:** any OTHER row stuck in the shared erasure queue (another member's, or an old one) | `vault erasure still owed` with `artifactsQueued: 0` | Fixed by X4: this no longer raises the alert, though the log line remains for an operator (probes FQ-1, SB-4, SB-5) |
| R4 | Removing a Work (the Work route, or a Delete that takes its Work with it): the Work's own image bytes are owed | `[living-works] Work removed; its image bytes are still owed destruction`, or the manuscript route's `vault erasure still owed` | The body says `unconfirmed:{image:true}`; the member is told about the image, not the original file (probe WI-1) |

A bare 500 `{error:'Failed to remove manuscript'}` is a different thing, and it is **not** proof that nothing was deleted: it is what an exception inside the erase transaction produces (rolled back, nothing deleted: probe F-2) and also what an exception AFTER the commit would produce (the sweep or the custody read failing). The client therefore treats it as "we could not confirm", re-reads Home, and never says "nothing was removed" about it.

### 6.2b Disposition of round 4 (each of the 29 that stood)

### 6.2c Disposition of round 5 (each of the 27 that stood)

Round 5 reviewed the round-4 fixes and found that one of them was itself a defect, and that the page still guessed in one place. Both are closed in the design, not in a test.

- **The image-row lock inverted the lock order (found, reproduced on PostgreSQL 16, and mine).** Round 4 added `FOR UPDATE` to the Work's image row in both routes (SRV-4). In the Work route the image row was read, and so locked, BEFORE the Work row; the erase locks the Work row first. For any Work that has an image, a Delete of its writing and a Remove of the Work could deadlock (40P01, one of them a 500 for an act that did not happen). The probes had not seen it because no probe drove a Delete and a Remove of the SAME Work that has an image (DL-2's pair, a loose Delete of a writing two Works hold, refuses 409 before it ever reads an image row, so even an image on that Work could not expose the cycle: the sixth review showed this). Remove now locks the Work row first. DL-3 holds a Delete part-way (it holds the Work row, waiting at the writing's source arrival) and sends the Remove, so the old order cannot pass; DL-2 now alternates its old topology with sole-claimant pairs that can reach the image row. **Superseded 2026-11-06, see 6.9.1:** since the follow-up the Remove takes the recovery-capture advisory lock before any row, so in DL-3 the Remove now waits at that key, having taken no row lock at all (DL-3 asserts exactly that), and DL-2's sole-claimant pairs are serialised at the key. Neither reaches the Work-row-before-image-row order any more. That order is now probed by DL-3b (a transaction holds the Work row without the key and a Remove arrives), and guarded by the hermetic LOCK ORDER tests (`deleteRoute.test.ts`) and candidates S21 and J23. The reasoning of this paragraph about why the old order deadlocked stands as history.
- **The server says what became of the Work; the page does not guess.** Round 4 still chose between "this card becomes a *deleted* card" and "the Work stays" from the card's own picture of the Work (kind `writing` vs `writing-keeps-work`). A card with a stale picture could turn a Work the server kept into a permanent "was deleted" card, hiding a live Work from Home. The manuscripts route now answers `{removed, workRemoved}` on the 200 as well as on the 500; the client carries it (`ActResult`, `DeletionUnconfirmed.workRemoved`); the door settles into a "deleted"/"removed" card only on `workRemoved: true`, says "The Work stays" only on `workRemoved: false`, and says only "that writing was already gone" when the server did not say (a 404). The card's picture still decides the wording of the question BEFORE the act, which is the member's to confirm.

- **A Remove can now wait, with no timeout, behind the recovery-capture lock.** The key is one global constant, not per member. *Who holds it today:* the only code in this tree that takes it is the writing Delete (`eraseManuscript.ts`, at the top of its transaction, which also runs the R20 editorial-history erase and the X8 cleanup) and, in the follow-up, the Remove route (`takeRecoveryCaptureLock` in `lib/manuscript/source/workDeletionRecord.ts`), which an empty-Work Delete also uses. Each holds it for its whole transaction. That duration was not measured; what the source shows is that the transaction makes no call outside the database (the byte destruction and the seal run after it commits). A coherent R20 backup is documented to hold it too (`eraseManuscript.ts`, comment at lines 99-102 at commit:`7add1a9f925850aa3e8338893e7bf896399c7e8b`), but no such backup caller was found in the tree (a search of the repository for the key's name finds only those two source files, their tests, probes and defeat-candidate runner, and this record); whether any job outside the repository takes it is not established (6.9.5). `lib/db/postgres.ts` sets a pool `max` of 20 and `connectionTimeoutMillis` of 2000 (which bounds waiting for a free client, not for a lock) and sets no `statement_timeout` or `lock_timeout`. Every Remove that waits pins a pooled connection; with 20 pinned, unrelated requests fail to get a client within two seconds. A Delete already has this exposure; Remove widens it. A bounded wait is owed (6.9.5), and it has a condition on when it must land.
- **Remove now fails closed on its own record.** In the follow-up the manifest and the `living_works` tombstone are written in the same transaction as the Work's deletion (`deletion_manifests`, `provenance_tombstones`; `writeWorkDeletionRecord` throws if the manifest returns no id). Before the follow-up Remove did not depend on those tables, so it can now fail where it did not before; the route comment and the tests (`deleteRoute.test.ts`: `failManifest`, `manifestEmpty`, `failTombstone`) pin the behaviour. The member is told nothing false (the Work does stay), but a Remove that fails this way offers no cause.
- **An empty-Work Delete is recorded too, in the follow-up.** A card with no writing sends its Delete to the Work route (`lib/writersStudio/deleteWork.ts` lines 135-143 at that commit), which is the Remove route, so the same record is written for it.
- **A restore.** `scripts/restore-governed.sh` exports the live deletion manifests, scopes and tombstones before a restore, re-applies them afterwards, and then deletes any restored row that a tombstone names (for every `object_kind` other than `member_manuscripts` whose table exists, matching `object_id` to the row id).
