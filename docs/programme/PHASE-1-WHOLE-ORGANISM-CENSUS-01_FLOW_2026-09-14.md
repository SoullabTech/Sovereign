## 0 · Purpose

Determine, from the actual Soullab organism:

> What exists? What is live? What participates? What has authority? What is merely present? What
> is missing, duplicated, dormant, blocked, or contradicted?

Then compare that organism against the strategic choices Soullab has actually made.

**This flow does not decide what Soullab should become.** It produces the evidence from which the
founder can make that decision.

## 3 · P1-01 · GOVERNING SOURCE READ

Before repository interpretation, Jarvis identifies the governing canon for each subsystem. For
every source:

```text
SOURCE
DATE / SHA
STATUS
JURISDICTION
WHAT IT SETTLES
WHAT IT DOES NOT SETTLE
CURRENT / SUPERSEDED / HISTORICAL ONLY
```

### Rule

⭐ **Do not infer architecture from aspiration.**

```text
a design document   proves   design
a migration         proves   a migration exists
a type              proves   a type exists
a table             proves   a table exists
an import           proves   an import exists
```

None of those independently proves that a capability is **participating in canonical runtime**.

## 4 · P1-02 · PARALLEL ORGANISM CENSUS

Jarvis may dispatch bounded census workers. **Workers produce evidence, not rulings.**

⛔ They may not: repair what they find · refactor · change schema · reconnect dormant systems ·
activate capabilities · consolidate duplicates · delete obsolete substrate · normalize
disagreements · invent missing architecture · open implementation work.

Each worker returns a **record-only census.**

### Census domains

**A · Canonical cognition / MAIA.** Trace:

```text
member input
→ sensory/input boundary
→ context construction
→ canonical cognition
→ model/provider dispatch
→ response construction
→ member-facing output
```

Determine where MAIA's identity, reasoning, authority and canonical response path actually reside.

**B · Memory / Anamnesis.** Trace each meaningful memory capability through:

```text
EXISTS → COMPUTED → PERSISTED → LOADED → SURFACED → UPDATED
```

⛔ Do not collapse database presence into runtime participation.

**C · Developmental + relational memory.** Identify developmental observations · relationship
continuity · member formulations · episodic structures · preference/semantic memory ·
practitioner-related memory · the authority governing each. Determine whether these form one
system, multiple systems, or overlapping substrates.

**D · Field intelligence.** Census independently: Resonant Field Intelligence · Unified Field ·
coherence/field computation · field-related stores · field-related prompts/context · any
member-facing field surfaces. Separate:

```text
computation ≠ persistence ≠ canonical participation ≠ product surface ≠ ontological claim
```

**E · Spiralogic / Elemental intelligence.** Trace where it is encoded · computed · invoked ·
persisted · surfaced · allowed to influence canonical cognition. Distinguish **framework
vocabulary** from **executable intelligence**.

**F · Symbolic systems.** For each, determine whether it is informational · interpretive ·
computational · memory-bearing · runtime-participating · member-facing · dormant. ⛔ Do not infer
authority from symbolic sophistication.

**G · Model / provider / orchestration organism.** Trace:

```text
capability declared → capability selected → arguments validated → governance admitted/refused
→ packet constrained → provider/model dispatched → result returned → receipt/evidence persisted
```

Distinguish: `provider ≠ model ≠ cognition ≠ MAIA identity ≠ authority`.

**H · Sensory / voice organism.** Trace independently from canonical cognition:

```text
capture → STT → canonical cognition → response → TTS → re-listen / continuation
```

Determine where sensory infrastructure ends and cognitive authority begins. ⛔ A transport or voice
mechanism must not be mistaken for an alternate MAIA.

**I · Member / practitioner organism.** Map the actual relationship among member · MAIA ·
practitioner · practitioner-facing surfaces · member-private material · explicit sharing gestures ·
derived practitioner information.

> **F9 boundary.** This census does not turn F9 into a work programme. If evidence concerning
> indirect visibility naturally appears during the whole-organism census, record it. ⛔ Do not
> launch a separate F9 assurance project, privacy repair, or new subsystem under this authority.

## 5 · P1-03 · COMMON EVIDENCE SCHEMA

Every census finding uses the same vocabulary.

```text
ORPHANED · BLOCKED · SUPERSEDED · DOCUMENTATION-ONLY · UNKNOWN
```

⛔ **No softer synonym may replace `UNKNOWN` when evidence is absent.**

### Every capability record answers

```text
CAPABILITY
DECLARED WHERE · COMPUTED WHERE · PERSISTED WHERE · LOADED WHERE · SURFACED WHERE · UPDATED WHERE
CANONICAL CALL PATH · UPSTREAM DEPENDENCIES · DOWNSTREAM CONSUMERS
MEMBER AUTHORITY · MAIA AUTHORITY · PRACTITIONER AUTHORITY · SYSTEM AUTHORITY
GOVERNANCE GATE · FAILURE MODE · CURRENT STATUS
SOURCE EVIDENCE · CONTRADICTIONS · UNRESOLVED QUESTIONS
```

### Evidence rule

⭐ A claim of `LIVE` requires a **demonstrated live path**. Imports, declarations, types, routes,
tables or historical documents alone are insufficient.

## 6 · P1-04 · WHOLE-ORGANISM ASSEMBLY

Jarvis waits until all required census domains return. ⛔ No organism-level synthesis while
required parts are still outstanding.

- **MAP 1 — Capability graph.** What can the organism actually do?
- **MAP 2 — Participation graph.** What actually participates in canonical MAIA activity?
- **MAP 3 — Authority graph.** Who or what is allowed to cause consequential effects?

Explicitly preserve:

```text
EXISTS        ≠ PARTICIPATES
PARTICIPATES  ≠ DECIDES
KNOWS         ≠ CONSIDERS
CONSIDERS     ≠ CONTRIBUTES
CONTRIBUTES   ≠ HAS AUTHORITY
INFERENCE     ≠ RELATIONAL AUTHORITY
```

- **MAP 4 — Failure / discontinuity graph.** Broken edges · dead ends · competing paths · duplicate
  authorities · shadow implementations · dormant systems · historical systems still appearing
  current · documentation that overstates implementation · implementation that outran governing
  doctrine · governance-blocked capabilities.

⛔ No repairs.

## 7 · P1-05 · CONTRADICTION / GAP PASS

For every contradiction, record **both sides**. ⛔ Never smooth disagreement into a synthetic
answer.

Classify each finding:

```text
ABSENCE · CONTRADICTION · DUPLICATION · DORMANCY · AUTHORITY COLLISION
DOCUMENTATION DRIFT · IMPLEMENTATION DRIFT · UNPROVEN PARTICIPATION
UNLOCATED GOVERNANCE · UNKNOWN
```

For each:

```text
WHAT THE SYSTEM APPEARS TO CLAIM
WHAT THE EVIDENCE SHOWS
WHY THE DIFFERENCE MATTERS
WHETHER FOUNDER RULING IS REQUIRED
```

⛔ No *minimum repair set* is authorized during this phase. Where a later repair might be necessary,
record: **REPAIR QUESTION MAY EXIST — NOT YET AUTHORIZED.**

### Part VII admission tests

```text
important   ≠ strategic
canonical   ≠ strategic
expensive   ≠ strategic
a gate      ≠ strategic
an epistemic hold        ≠ strategic
an implementation choice ≠ strategic
```

And: ⭐ *when a candidate rule names a vendor, model, library, route, database, gate, test, or
present implementation, ask what principle would remain if that mechanism were replaced completely.
If a higher rule survives replacement, the mechanism belongs underneath it.*
