## What was implemented in the isolated branch

**New source intake is routed in code through** `ingestSourceWithCustodyCandidate` (`app/api/writers-studio/sources/route.ts`) **only after** the unchanged, unconditional, server-side fail-closed guard `sourceUploadPostureAuthorized(): false`. Beta eligibility still precedes parsing or persistence. Candidate adapters are not invoked while the guard remains closed. `PATCH /api/writers-studio/sources/[id]` has its own independent hard-false guard (`sourceReviewedEditAuthorized`) so future approval of new source uploads cannot accidentally unlock the still-unsafe existing reviewed-text writer.

The candidate has five coordinated components:

- `sourceCustodyReservations.ts` — authenticated session row lock and **committed** DB reservation before any source bytes reach disk. The SQL trigger revalidates membership, active session and ordinary posture. Reservation status is never derived from a browser flag.
- `sourceCustodyFiles.ts` — durable content-free intent journal, create-only staging, validated original filename, extraction from staged bytes, directory publication, and journal reconciliation after a database-proved outcome. Duplicate originals, unknown paths and incomplete canonical originals are rejected. Missing journal can be retried only when existing bytes independently prove the outcome; corrupt journals do not grant cleanup authority.
- `sourceCustodyIngestCandidate.ts` — input checks, in-memory read, reservation → stage → writing state → extraction → publish → DB finalization → journal cleanup. Extraction failure retains a deliberately commissioned original in an error state with a generic error message. A thrown DB COMMIT acknowledgment triggers durable state lookup before any attempted cleanup, so a successful but unacknowledged commit is not mistaken for an abort.
- `sourceCustodyRuntimeCandidate.ts` — canonical adapters: final `workbench_uploads` row plus terminal custody status are written through one PostgreSQL transaction/client; a settled writer can recover a rejected operation with the custody row locked, filesystem deletion/fsync first, and DB abort only afterward. **Unattended recovery of an arbitrarily crashed worker is not admitted** without verified worker quiescence and exclusive recovery ownership.
- `Caddyfile` — `SOURCE-CUSTODY-EDGE-01` is a **candidate** write fence in the existing `deny_disabled_routes` snippet used by the production public sites. It denies `POST`, `PATCH` and `PUT` to source collection/item endpoints with HTTP 423. GET and DELETE remain unaffected. This compensates for the old production application, which has no Sanctuary guard and whose reviewed-text PATCH writes filesystem bytes before its DB query.
