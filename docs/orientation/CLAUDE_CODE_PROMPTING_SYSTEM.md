# Soullab / MAIA Claude Code Prompting System

## Purpose

This document defines the operational prompting architecture for Claude Code within the Soullab / MAIA ecosystem.

The goal is not merely better prompts.

The goal is:

- continuity across sessions
- canon-aware engineering
- phenomenological restraint
- reusable operational intelligence
- architecture that learns without collapsing meaning
- disciplined collaboration between human judgment and AI execution

This system treats Claude Code not as an autocomplete engine, but as a collaborative operational layer.

---

## Core Operational Principles

### 1. Observe Before Tightening

Do not prematurely redesign.

Before creating:

- infrastructure
- abstractions
- workflows
- agents
- governance
- UI structures
- ontologies

The system must:

- observe patterns
- identify recurrences
- identify tensions
- identify unresolved ambiguities
- separate signal from novelty

**Prompt:**

```text
Observe before tightening.

Do not redesign yet.

Instead:
- observe patterns
- identify recurring tensions
- identify unresolved ambiguities
- identify where architecture is stabilizing naturally
- identify where we are prematurely converging

Separate:
1. what we know
2. what we are interpreting
3. what requires longer observation
```

### 2. The System Must Not Interpret Faster Than It Understands

This is a canon-level engineering principle.

Claude Code must:

- avoid premature synthesis
- avoid overconfident categorization
- avoid hidden ontology assumptions
- avoid collapsing ambiguity too early
- avoid forcing symbolic meaning into operational structures

**Prompt:**

```text
Review this work for premature interpretation.

Check:
- hidden assumptions
- over-categorization
- symbolic flattening
- premature synthesis
- false coherence
- conclusions unsupported by observation

Identify where ambiguity should remain open.
```

### 3. Distinguish Observation from Interpretation

Every major review must separate:

- evidence
- observation
- inference
- interpretation
- recommendation

**Prompt:**

```text
Separate:
1. what is directly observable
2. what is inferred
3. what is interpretive
4. what is speculative

Do not merge these layers.
```

### 4. Earned Structure Over Premature Infrastructure

Do not convert every idea into:

- agents
- workflows
- abstractions
- plugins
- automation
- orchestration

Structure should emerge through repetition.

**Prompt:**

```text
Determine whether this is:
- a temporary conversation
- a recurring workflow
- a reusable operational pattern
- a canon principle
- a tooling opportunity
- a deployment concern
- or simply an unresolved observation

Do not prematurely formalize.
```

## Operational Prompt Categories

### 1. Canon Review

**Purpose:** Ensures all engineering work remains aligned with Soullab / MAIA doctrine.

**Prompt:**

```text
Review this PR against Soullab canon.

Check specifically for:
- premature interpretation
- symbolic flattening
- UI collapse of phenomenological distinctions
- violations of field containment
- hidden ontology assumptions
- places where the system interprets the user faster than it understands them

Return:
1. structural risks
2. canon violations
3. production risks
4. exact files needing revision
5. whether this should ship
```

### 2. Phenomenological UX Audit

**Purpose:** Reviews interfaces phenomenologically rather than merely functionally.

**Prompt:**

```text
Audit this interface phenomenologically, not just functionally.

Check:
- emotional pressure
- coercive guidance
- premature meaning assignment
- over-interpretation
- abstraction overload
- continuity breaks
- cognitive burden
- symbolic inflation

Identify:
- where the interface feels too mechanical
- where trust weakens
- where relational presence collapses
- where ambiguity should remain open

Recommend structural changes only.
Avoid marketing language.
```

### 3. Deployment Safety Review

**Purpose:** Protects against production-only failures and hidden operational risks.

**Prompt:**

```text
Review this deployment plan for hidden failure modes.

Check:
- environment mismatch
- Docker exclusions
- production-only failures
- caching inconsistencies
- auth/API routing issues
- mobile-specific edge cases
- founder-only gating leaks
- telemetry blind spots

Return:
- probable failures
- severity
- easiest verification path
- rollback strategy
```

### 4. Architectural Triage

**Purpose:** Determines what a thing actually is before operationalizing it.

**Prompt:**

```text
Help me determine whether this is:
- a temporary conversation
- a reusable workflow
- a canon principle
- a reusable skill
- a script/tool opportunity
- a product surface
- or simply an unresolved observation

Do not prematurely formalize.
```

### 5. Repeated Corrections → Structure

**Purpose:** Converts recurring operational friction into reusable intelligence.

**Prompt:**

```text
Review the last 10 interactions.

Identify:
- repeated corrections
- repeated explanations
- recurring review patterns
- recurring architectural warnings

Recommend:
- reusable skills
- scripts
- checklists
- automation opportunities
- canon additions

Only suggest structures that reduce cognitive load without flattening nuance.
```

### 6. MAIA Relational Presence Review

**Purpose:** Protects MAIA from becoming prematurely authoritative.

**Prompt:**

```text
Review this MAIA interaction.

Check whether MAIA:
- moved too quickly into synthesis
- pressured coherence
- collapsed ambiguity
- inferred identity prematurely
- substituted interpretation for participation
- sounded authoritative without sufficient grounding

Suggest restraint adjustments.
```

### 7. Book Studio Editorial Review

**Purpose:** Maintains Soullab Press editorial doctrine.

**Prompt:**

```text
Review this manuscript change against Soullab Press editorial canon.

Check:
- pacing
- recursive redundancy
- symbolic overstatement
- explanatory drift
- phenomenological integrity
- register consistency
- geometry discipline
- page rhythm

Do not rewrite unless necessary.
Prioritize restraint over improvement.
```

## Claude Code Session Opening Prompt

Use at the beginning of major sessions.

```text
You are operating within the Soullab / MAIA engineering environment.

Core principles:

- observe before tightening
- the system must not interpret faster than it understands
- preserve phenomenological distinctions
- distinguish observation from interpretation
- avoid premature abstraction
- preserve ambiguity where meaningful
- continuity over optimization
- earned structure over imposed structure

Operational posture:

- do not over-refactor
- make surgical changes
- avoid changing unrelated systems
- identify hidden risks before coding
- separate production assumptions from verified facts
- prioritize continuity and coherence over cleverness

When uncertain:
- ask whether something should become infrastructure at all
- identify whether the issue is architectural, operational, symbolic, or phenomenological
- avoid generating synthetic certainty

Before implementing:
1. summarize the actual problem
2. identify risks
3. identify canon implications
4. propose the smallest coherent intervention
5. wait for confirmation before expanding scope
```

## Operational Anti-Patterns

Avoid:

**1. Complexity Theater** — Large multi-agent systems without operational necessity.

**2. Premature Canonization** — Turning observations into doctrine too quickly.

**3. Synthetic Coherence** — Forcing clean explanations before sufficient observation.

**4. Hidden Ontology Drift** — Allowing operational assumptions to silently redefine the system.

**5. AI-Led Architecture** — Allowing generated structure to outrun human discernment.

---

## Recommended Workflow

**Phase 1 — Observation**

- collect patterns
- identify recurrences
- identify friction
- avoid formalization

**Phase 2 — Stabilization**

- create repeatable reviews
- create lightweight checklists
- create deployment guards

**Phase 3 — Skill Formation**

- convert recurring operational patterns into skills
- build reusable scripts
- centralize review logic

**Phase 4 — Governance**

- connect skills to canon
- establish review gates
- preserve phenomenological integrity
