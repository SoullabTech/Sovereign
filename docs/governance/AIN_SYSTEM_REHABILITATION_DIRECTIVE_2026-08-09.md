# AIN SYSTEM REHABILITATION — FOUNDER DIRECTIVE

**Date:** 2026-08-09
**Author:** Kelly Nezat (founder), issued in session; recorded verbatim-in-substance by Claude Code the same day
**Status:** Standing founder directive — governs the rehabilitation phase until amended by the founder
**Companion artifact:** `docs/architecture/AIN_SYSTEM_REHABILITATION_MAP.md` (coordination infrastructure created under this directive — the map is NOT a source of constitutional authority)

---

## 1. What this directive is

AIN enters a **rehabilitation and integration phase**. The objective is not to add
features wherever a gap appears. Recent audits show that AIN frequently already
contains the necessary substrate, capability, route, data, or governance mechanism —
but disconnected, unreachable, behaviorally unused, duplicated, incompletely
governed, or represented through an obsolete abstraction.

The danger this directive exists to prevent: **twenty locally correct repairs that
never complete the system-level integration.** Lane-by-lane forensic work is
excellent; it must now serve one coherent AIN OS rather than another layer of patches.

## 2. Precedence of work

> **discover → establish authority → recover → reconcile → connect → repair →
> simplify → verify → optimize → only then create.**

Before implementing any apparently missing capability, prove which of these it is:

1. genuinely absent;
2. implemented but unreachable;
3. available but not selected;
4. persisted but unread;
5. duplicated;
6. attached to the wrong owner/domain;
7. blocked by obsolete routing or eligibility;
8. missing governance;
9. unsafe to activate;
10. genuinely ready for new implementation.

Do not default to incremental patches. Evaluate the complete relevant architecture
first. Preserve valuable existing structures — but when evidence demonstrates that
ownership, routing, composition, or boundaries are structurally wrong, propose the
coherent structural correction rather than accumulating compatibility patches.

## 3. Authority ordering

Existing founder rulings and ratified constitutional records **outrank**:
implementation convenience · historical route ancestry · current UI placement ·
telemetry · candidate architecture.

Never silently convert an observation, candidate, provisional finding, or
lane-level heuristic into canon.

## 4. The Rehabilitation Map

One **AIN SYSTEM REHABILITATION MAP** is maintained, **referencing — not
duplicating —** the authoritative audits and rulings. For every discovered
capability/subsystem it records:

> intended capability · canonical substrate · current implementation · production
> use · reachability · governance state · known defect · blocking ruling · required
> repair/integration · verification criterion · disposition

Dispositions: **PRESERVE · RECONNECT · REPAIR · RECONCILE · CONSOLIDATE ·
COMPLETE · DEPRECATE · BUILD · HOLD**

The map is coordination infrastructure, not a new source of constitutional
authority. It must distinguish:

> **implemented ≠ available ≠ reachable ≠ selected ≠ exercised ≠ verified ≠ sustained.**

(This incorporates the capability lifecycle without prematurely constitutionalizing
the provisional Week 1 finding.)

## 5. Rehabilitation layers (sequence is binding)

**Layer 0 — Constitutional reconciliation.** Before structural implementation,
propagate rulings that already exist: ratified ruling → documents → candidate
architectures → implementation assumptions → tests → runtime. Identify
contradictions. Do not let old candidate architecture quietly survive after a
ruling supersedes it. This establishes trustworthy ground.

**Layer 1 — Security, identity, authority and consent.** Before convenient UX.
Establish the five-axis architecture — **Identity · Ownership ·
Relationship/Participation · Consent · Confidentiality** — but do NOT create one
enormous generic authorization function. Authority remains **act-scoped**:
`Actor → Authority substrate → Subject → Act → Object → Recipient`, allowing
different legitimate substrates (practitioner-client administration · constituted
relationship · encounter participation · Co-Lab membership · explicit sharing ·
program participation). Then repair confirmed defects systematically.

**Layer 2 — Memory ecology.** Strong restraint on building. The job is
**inventory → provenance repair → forgetting semantics → reader/composition
architecture → activation**, NOT new memory tables. Eventually connect: memory
atoms · episodic memory · `memory_links` · `relationship_entries` ·
trajectory/progression structures · reinterpretations · memory-use history ·
Keeps · relational history — through a **governed reader** that can perceive
relationships without laundering inference into canonical memory.

**Layer 3 — House rehabilitation.** The member-facing payoff. House is designed
around both *what belongs to my life* and *what I actually need to do*, at roughly
three levels: **Immediate gestures** (Talk · Reflect · Journal/Write · Keep ·
Note · Decide) · **My world** (Relationships · Reflections · Decisions · Changes ·
Keeps/Memory · Files) · **Places to work** (Writer's Studio · Practitioner Studio ·
Vision Studio · Co-Lab · …). Studios receive entitlement behavior: Steward →
enter; non-Steward after beta → see Studio offering + invitation to become
Steward. **No maze of interior paywalls.** Do not build all of this blindly —
Relationships can likely surface quickly (canonical member route exists);
Reflections and Decisions need already-scoped traces.

**Layer 4 — Studio rehabilitation.** Clean up the 40/17/32 drift
(≈40 directories ≠ 17 navigation entries ≠ 32 module records) — but only AFTER
House ownership is clear. Classify each Studio surface: actual Studio instrument ·
projection of a House domain · obsolete · duplicate · orphaned · intentionally
hidden. Then simplify. Expect deletion and consolidation, not additions.

**Layer 5 — Inference and development economics.** Target:
`task → classification → cheapest competent model → verification → escalation`
(local → cheap/mechanical/exploratory; Kimi → substantial coding/implementation/
tests; Claude → difficult architecture, security, constitutional reasoning, failed
escalations). Prove equivalence before automatic routing. The metric is NOT
"Kimi works" — it is **Anthropic expenditure displaced without engineering
quality loss.**

## 6. Redefinition of "done" — the proof ladder

A capability is no longer considered restored because tests pass. Rehabilitation
work requires the ladder:

| Rung | Meaning |
|---|---|
| **Exists** | canonical substrate identified |
| **Correct** | architecture conforms to rulings |
| **Secure** | authority/consent boundaries tested |
| **Connected** | actual caller/reader exists |
| **Reachable** | intended user can get to it |
| **Exercised** | pathway run end-to-end |
| **Observable** | we can tell whether it is actually being used |
| **Sustained** | mechanism detects future drift/loss |

Different failure states need different repairs — e.g. `memory_links`: Exists but
not Connected. Relationship ceremony: Exists + Reachable but not Exercised
(Practice Fields never became live). Kimi: Exists + Available but not Selected.
Relationships: Exists + used, but poorly House-Reachable.

## 7. Guards after rehabilitation

Once a repaired architecture is demonstrated, ask: **what allowed this capability
to disappear from lived operation without anything failing?** Then add the
smallest appropriate structural protection. Examples: registered module without
reachable doorway → CI detects it; API route outside access-control inventory →
CI fails; governed memory substrate unexpectedly without reader/writer →
capability audit flags it; canonical House domain without member reachability →
architecture test; route taking person identity directly from caller where
authority requires resolved subject → security test; provider integration
receiving zero traffic despite intended routing → observability warning.

Not every capability needs a hard gate. Important capabilities need
**loss detection**.

## 8. Working rules

- The instruction is not "fix all these problems" — it is: **rehabilitate AIN into
  the system its existing architecture and founder rulings already imply.**
- Work **one bounded rehabilitation unit at a time**, returning evidence before
  crossing into the next layer.
- Start with the System Rehabilitation Map, not implementation. Synthesize the
  existing audits' status and dependencies **without reopening their conclusions**.
- The end state per capability: latent architecture → coherent architecture →
  lived capability → protected capability.

The founder ratified this directive as *"the right governing frame"* and added two
binding clarifications:

**(a) Phase definition.** AIN's current phase is **system completion**, not
feature development. The system is not simply "unfinished": substantial portions
of the intended OS already exist in fragments at different levels of realization —
mature substrates without readers · sophisticated mechanisms disconnected by later
refactors · correctly governed but unreachable capabilities · reachable but
constitutionally wrong surfaces · duplicates that exist because the canonical
layer was never established · and some genuine absences. **Rehabilitation means
discovering which is which before adding anything.** The individual discoveries
(COGOS, memory, Kimi, relationship constitution, Practice Fields, Now What?,

than it has successfully integrated into lived operation.*

**(b) Map-shape guard.** The Rehabilitation Map must NOT become another giant
architectural specification. Its power is being a **control surface over
authoritative evidence** — it points outward and never gradually absorbs the
reasoning from the lanes. Canonical row shape:

```text
CAPABILITY
    ↓

    ↓
authoritative ruling/audit
    ↓
current lifecycle state
    ↓
defect/blocker
    ↓
disposition
    ↓

    ↓
```

A map row that starts explaining *why* instead of citing *where the why lives*

**latent architecture → coherent architecture → lived capability → protected capability.**

## 10. Layer 2 acceptance — the relational continuity test (founder, same day)

The founder set the acceptance frame for the memory-ecology layer:

**The goal is not that MAIA "remembers more" — it is that her memory becomes
usable.** The substrate is already substantial (conversation history, memory-use
records, episodic memory, strong isolation, stewarded atoms). The failures are
higher-order: corrections don't persist · DEEP loses context · wisdom isn't
reaching live conversation · return posture is flat · some health signals are
misleading. Fixing those turns raw stored memory into **relational continuity**.

The upgrade, in the founder's words, is moving from
*"I have lots of stored records about you"* to
*"I know what is current, what changed, what was corrected, what matters now,
what is mine to infer, what came from wisdom, and how to meet you from
continuity."*

The most noticeable change to testers should be **felt continuity**, not raw
recall quantity: MAIA feels less like she occasionally retrieves memories and
more like she has been in an ongoing relationship with the member.

**Binding acceptance test — Layer 2 is not done until this passes against
production-equivalent paths:**

> Can MAIA meet someone over many sessions, misunderstand them, be corrected,
> retain the correction, go deep with context intact, draw appropriately on
> wisdom, and meet them again weeks later — without confusing old, inferred,
> private, or external material with the member's current truth?

Component capabilities the test implies (each must hold simultaneously, and
consent · sanctuary · provenance · member boundaries are preserved throughout):

1. remember important things across sessions without dragging in stale
   misunderstandings;
2. retain corrections and stop resurfacing superseded material as current truth;
3. distinguish what the member said ≠ what MAIA inferred ≠ what external wisdom
   says;
4. carry continuity into DEEP conversations instead of becoming context-blind
   there;
5. bring in relevant AIN Vault / Library wisdom at the right moments;
6. recognize meaningful return after absence;
7. preserve consent, sanctuary, provenance, and member boundaries while doing
   all of the above;
8. handle long-term developmental arcs.

**What this does NOT promise:** perfect "human-like lifelong memory." Quality
still depends on what gets captured, how retrieval/ranking works, and how much
context each model lane can use effectively — the program's job is to make those
three **coherent rather than accidental**.

No Layer 2 rehabilitation unit may be declared complete against a lesser
standard than this test; per-row verification criteria in the map are
necessary, not sufficient.

### §10.1 Founder clarifications (same day)

**(a) The unit of success.** §10 changes not the scope of Layer 2 but its unit
of success. Previously, individual memory mechanisms could satisfy their own
verification criteria while the member still experienced discontinuity — a
category error §10 forecloses. The hierarchy:

```text
individual mechanism works
        ↓
records persist correctly
        ↓
retrieval / ranking works
        ↓
provenance remains intact
        ↓
corrections survive
        ↓
current vs superseded meaning is distinguished
        ↓
relevant context reaches the encounter
        ↓
MAIA responds from that continuity
        ↓
MEMBER EXPERIENCES: "She remembers me."
```

The last transition is the one that matters. Everything above it is necessary
infrastructure and proof; none individually establishes the lived consequence.
The eight-part test invents no new systems — every clause has an architectural
referent in the rehabilitation map. It is an **integration/acceptance test
across Layer 2**, not an expansion of Layer 2.

**(b) Temporal and epistemic discrimination.** *Remembering more is not the
same as knowing what matters now.* A system with excellent archival recall can
feel LESS relational if obsolete interpretations, withdrawn ideas, superseded
decisions, or contextless fragments keep resurfacing. The upgrade is partly
retrieval, but substantially discrimination among:

> **current · changed · corrected · withdrawn · inferred · declared ·
> externally sourced · contextually relevant now.**

That discrimination is what human beings experience as being remembered.

**(c) The proof relation is bidirectional — both required.**

> Row verification is necessary but insufficient. The relational acceptance
> walk is necessary but does not replace row verification. **Layer 2 completion
> requires both.**

This protects in both directions: against engineering declaring victory because
the machinery works, and against a compelling MAIA interaction being mistaken
for proof that the machinery underneath it is sound. If every row is green but
the walk fails, Layer 2 fails; a convincing conversation cannot substitute for
demonstrating that corrections, provenance, selection, and DEEP context behaved
correctly underneath it.

**(d) The defensible outward claim** (under
`docs/canon/MARKETING_CLAIM_DISCIPLINE.md`): not human-like lifelong memory,
but that **AIN has made continuity deliberate rather than accidental, and can
demonstrate that this results in a person being met in light of what has
actually unfolded between them across time.**

### §10.2 Acceptance and closure (founder ruling, same day)

**ACCEPTED.** §10 and §10.1 are complete for this layer. This design boundary
is closed; no further doctrine is added in this lane.

1. **Non-extension.** The acceptance-instrument pattern is NOT extended to
   Layers 1 or 3 in this lane. The possible symmetry is recorded as a **future
   governance question only**; those founder-level acceptance tests may not be
   authored by analogy.
2. **Ladder integrity.** No lower-level success condition — stored rows,
   successful retrieval, prompt inclusion, correct provenance, even technically
   correct recall — may individually be treated as proof of the final lived
   capacity (*"She remembers me"*).
3. **Discrimination over recall.** Do not optimize toward maximal recall at the
   expense of relational relevance. Excellent archival retrieval can still
   produce poor relational memory.
4. **Evidentiary jurisdiction.** Row evidence establishes machinery/capability;
   integrated-walk evidence establishes lived operation; completion requires
   their conjunction. **Neither may inherit the evidentiary jurisdiction of the
   other.**
5. **Completion language.** Do not report *"deep memory complete," "relational
   continuity proven," "MAIA remembers members,"* or equivalents from row-level
   evidence alone. Likewise, do not retire failed or unproven rows because an
   integrated encounter appeared successful.
6. **Outward claims.** Any external description stays within
   `docs/canon/MARKETING_CLAIM_DISCIPLINE.md`. Do not market architectural
   reachability as lived completion.
7. **Boundary.** Remain at D2: everything currently uncommitted stays
   uncommitted until this work is reviewed as a bounded artifact.

**Consequence for the MAIA readiness program (founder direction, recorded —
not an implementation authorization):** the eventual **golden-member test
should probably become the Layer 2 walk**, rather than a new acceptance
instrument beside it. The E1–E14 machinery can prove individual capacities;
the longitudinal encounter then asks the integrated question: *after everything
that has happened between us, does the way MAIA meets me now make sense because
of what has actually unfolded?*
