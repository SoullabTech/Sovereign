# Programme: JARVIS Living Spiral

**Purpose:** Create the operational development cockpit through which one founder can coherently
research, build, understand, debug, verify, deploy, and evolve the full AIN/MAIA ecosystem while
preserving the whole.

## 0. GOVERNING PURPOSE

JARVIS Living Spiral is not a dashboard, task manager, issue tracker, or second source of system truth.

It is the spatial development memory, evidence projection, and stewardship cockpit through which one person can work on the entire AIN/MAIA ecosystem without having to mentally reconstruct:

- what exists
- how systems relate
- what is being developed
- what is deployed
- what is actually working
- what is broken
- what is unknown
- what evidence exists
- what has changed
- what depends on the current work
- what requires verification
- what requires human witness
- what requires founder authority
- where development should resume

The governing operational loop is:

```text
ORIENT → FOCUS → RESEARCH → DEVELOP → VERIFY → WITNESS → INTEGRATE → DEPLOY → RETURN TO WHOLE
```

JARVIS carries complexity.

The founder carries intention, meaning, architectural authority, and consequential decisions.

## 2. NON-NEGOTIABLE EPISTEMIC RULES

These rules govern every phase.

### 2.1 Absence must remain representable

JARVIS must be able to show:

- unknown
- unavailable
- not observed
- unresolved
- absent
- examined-and-negative

without converting these into invented state.

UNKNOWN ≠ FALSE.

MISSING ≠ EXAMINED AND NEGATIVE.

### 2.2 Every claim must carry a competence boundary

At evidence-bearing surfaces, render:

```text
WHAT THIS EVIDENCE ESTABLISHES
WHAT THIS EVIDENCE DOES NOT ESTABLISH
PLAUSIBLE WRONG READING / FAILING IMPLEMENTATION WOULD INSTEAD
```

The system must teach the reader how not to over-read its evidence.

### 2.3 VERIFY is not WITNESS

**VERIFY**

Technical evidence such as:

- tests
- CI
- code inspection
- runtime inspection
- API response verification
- database inspection

may clear:

`VERIFY_REQUIRED`

only within the scope actually established by that evidence.

**WITNESS**

A qualifying human encounter with the capability behaving as intended may clear:

`WITNESS_OWED`.

A capability may remain historically `witnessed` while acquiring a new `WITNESS_OWED` after a relevant change.

Do not rewrite historical witness.

### 2.4 Policy-generated debt must identify itself

Every generated verification or witness debt carries:

`basis`

Examples:

- `DIRECT_DEPENDENCY_CHANGE`
- `RUNTIME_CONTRACT_CHANGE`
- `CONSERVATIVE_UNKNOWN_IMPACT_POLICY`

A policy must never masquerade as a discovered fact.

### 2.5 Apertures are first-class entities

When JARVIS cannot observe something, create an aperture rather than filling the gap.

An aperture carries:

- domain
- missing observation
- why it matters
- claims it prevents
- possible instrument
- authority to instrument

Every aperture must render:

`THEREFORE NOT CLAIMABLE`

The prohibited claims derive mechanically from what the aperture cannot observe.

### 2.6 No unsupported topology

Never draw a dependency, causal edge, ownership relationship, or integration merely because it seems likely.

Negative invariant:

If an edge is not evidenced, do not draw it.

Positive invariant:

If an edge is evidenced and operationally relevant, make it navigable.

The graph is a view of evidence.

It is never a second place where topology is asserted.

### 2.7 Specifying derivation is not performing derivation

A proposed mechanism explaining how a state could be derived does not prove:

- that the source can currently be read
- that the derivation succeeds
- that the result is complete
- that the result is current
- that the assertion graph exists operationally

Maintain the distinction:

`SPECIFIED_DERIVATION`

versus

`PERFORMED_DERIVATION`

### 2.8 Review is not acceptance

`REVIEW COMPLETE` does not imply:

`PROTOTYPE ACCEPTED`

### 2.9 Acceptance is not build authority

`PROTOTYPE ACCEPTED` does not imply:

`BUILD AUTHORIZED`

### 2.10 Recording a defect is not authorization to repair it

A discovered defect is an observation.

It is not homework.

Use explicit states such as:

`DISCOVERED`
`VERIFY_REQUIRED`
`WITNESS_OWED`
`AWAITING_AUTHORITY`
`AUTHORIZED`
`BLOCKED_ON_PROOF`

## 21. SECURITY, CONSENT, AND IDENTITY

Living Spiral must never encourage bypassing security gates merely to achieve custody or deployment.

- remediation is authorized
- or a separately governed exception exists

Do not use:

- `--no-verify`
- silent hook bypass
- unauthorized data mutation
- consent rewriting
- identity merging

to force progression.

Identity consolidation, particularly where consent provenance differs, must be treated as a separately governed migration.

## 22. CUSTODY

Track independently:

- working-tree custody
- staging custody
- commit custody
- remote source custody
- canonical custody
- deployed custody

Do not collapse them.

Examples:

`UNTRACKED` is more precise than merely `UNCOMMITTED`.

`PUSHED` does not mean `CANONICAL`.

`MERGED` does not mean `DEPLOYED`.

`DEPLOYED` does not mean `WITNESSED`.

## 23. DEPLOYMENT READINESS

Never deploy merely because development completed.

Before any deploy, establish:

**Scope**
Exactly which commits/files/capabilities constitute the deploy unit?

**Canonical position**
What SHA is intended for deployment?

**Dependency coherence**
Are the changes mutually coherent?

**Migration state**
Any schema/data migrations?

**Identity/security effects**
Any authentication, consent, permissions, PHI, encryption, or session changes?

**Configuration**
Any environment variables, secrets, routing, container, native, or infrastructure effects?

**Verification**
What technical evidence exists?

**Witness**
What human-facing evidence exists?

**Known debt**
What remains knowingly broken/unverified?

**Rollback**
Can the deploy be reversed safely?

**Authority**
Has deployment itself been authorized?

## 24. DEPLOYMENT

When deployment is explicitly authorized:

1. Re-bind canonical source.
2. Confirm exact deploy SHA.
3. Confirm working tree does not contaminate the deploy.
4. Re-run required pre-deploy checks.
5. Confirm migrations and configuration.
6. Deploy using the established deployment path.
7. Record runtime identity/version.
8. Verify health endpoints and critical contracts.
9. Perform scoped runtime verification.
10. Perform required member/practitioner witness.
11. Compare expected vs observed state.
12. Record regressions or new apertures.
13. Do not call deployment complete until the required evidence exists.
