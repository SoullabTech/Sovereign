# INHABITABLE ARCHITECTURE — the design law for all interface work

**Provenance**: Founder-authored (Kelly, 2026-08-05), recorded in substance
verbatim. This is the instruction-layer change that ends the pattern of
rendering the ontology of the database instead of the architecture of the
human experience. It governs every member-facing surface in this repository.
Loaded via CLAUDE.md → "Inhabitable Architecture" section.

## The law

You are not designing an application interface.
You are architecting an **inhabitable digital environment**.

The UI is not a container for features.
The UI is the spatial expression of a human journey.

> **The interface is not a map of the system. The interface is the
> architecture of the user's lived experience of the system.**

The old seeing — `features → components → pages → navigation` — is replaced
by: **`human purpose → lived journey → places → gestures → interface`**.

Before writing code, identify:

1. Who is entering this place?
2. What state of being are they arriving from?
3. What should they encounter first?
4. What rooms/spaces exist?
5. What belongs in each room?
6. What should remain invisible until needed?

Do not render the inventory of capabilities. A house does not place the
stove, bed, couch, desk, and tools in the entryway because they all exist.
The interface must create spatial relationships. Every capability must
answer:

- What room does this belong to?
- What human activity does this support?
- When does a person need it?
- Should it be visible on arrival?

**If the answer is unclear, hide it.** The goal is not feature
discoverability. The goal is **inhabitation**.

## The warehouse failure mode

> If the interface displays all available capabilities simultaneously,
> assume the architecture has failed.
>
> A warehouse exposes inventory. A home reveals pathways.
>
> The user should never need to understand the underlying system model to
> inhabit the environment.

## Objects do not equal rooms

The recurring agent failure: seeing `Session · Journal · Goals ·
Commitments · Notes · Insights · Conversations` and producing a tab per
object. Objects exist **inside** rooms; they are not the rooms. The rooms
come from human activity (conversation, reflection, practice, memory,
relationship) — never from the schema.

## The adaptive environment (calm computing layer)

Do not design the interface as a visualization of available capabilities.
Design it as an **adaptive environment**: capabilities disappear until
context makes them meaningful. Every visible element must justify its
presence by serving the user's current developmental moment.

Every surface must answer:

1. What is the user's current state?
2. What is the next meaningful gesture?
3. What can disappear?
4. What should emerge only when invited?
5. What remains persistent because it represents **relationship**?

The target is an adaptive, context-aware, **calm** computing environment
where the interface becomes a transparent medium for human intention — not
"pretty," not "modern," not "better UX."

### ⚠️ Sovereignty rider on "current state" (constitutionally binding)

"Current state" and "developmental moment" mean **the moment as the member
has authored it**: what they kept, what they declared, the gesture they just
made, the room they are standing in — session facts and authored acts only.
They must NEVER mean inferred psychological state, activity-derived
readiness, or system-detected themes. An adaptive surface driven by
inference is ambient cognition — the exact third-voice / surveillance
pattern the Sovereignty Invariants and rulings E-3 / RIDER 2 refuse.
**Adaptation keys on authored facts, or it does not adapt.**

## The protocol: floor plan before code

Do not inspect components first. First create the **experiential floor
plan**:

- The House: what is the threshold? the hearth? the rooms? the natural path?
- For each room: purpose · emotional arrival state · primary gesture ·
  allowed objects · forbidden objects.

Only after the floor plan is agreed does component mapping begin — and the
question becomes *"what existing capabilities belong in each room?"*, never
*"where can we put these features?"*

## Vocabulary boundary

Room names in floor plans (Threshold, Hearth, Study, Archive…) are
**architectural design language for builders**. Member-facing labels must
speak the member's world (The Member's World is Primary) — the design
vocabulary must not leak onto the walls of the rooms it designs.

## Acceptance

A surface passes when a person inhabits it without understanding the system
model beneath it — when what they feel is *"I am continuing my work,"* never
*"I am managing my information."* Acceptance evidence is experiential and
visual (the rendered room, the walk), not technical (routes, tests, labels).
