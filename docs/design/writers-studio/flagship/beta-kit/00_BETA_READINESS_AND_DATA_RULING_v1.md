# SOULLAB WRITER'S STUDIO
# Beta Readiness + Participant Data Ruling v1

Status: FOUNDER / PRODUCT RESEARCH GOVERNANCE  
Purpose: prevent human beta evidence from being contaminated by unbuilt capabilities, ambiguous persistence, or unclear participant-data retention.

This record does not authorize implementation, schema mutation, deployment, or participant recruitment.

---

# 1. Core Law

> **A beta task may be run only when the candidate can actually express the product behavior the task is intended to measure.**

A participant's hesitation at an unbuilt capability is not usable evidence of usability.

Therefore:

- task existence ≠ task readiness;
- fixture existence ≠ beta environment readiness;
- facilitator consent ≠ system-retention consent;
- a green mechanical test ≠ a valid human study condition.

---

# 2. R9 Remains Gated

`R9 — Human Beta` is **NOT schedulable** merely because R8 is green.

1. the specific participant tasks being run are READY;

3. retention behavior is known and accurately disclosed;

# 4. Two Beta Phases

## PHASE A — CONTROLLED-MANUSCRIPT USABILITY BETA

Use:
- fixture manuscripts;
- Soullab-owned / founder-authorized manuscripts;
- explicitly licensed test material.

Purpose:
- comprehension;
- navigation;
- accessibility;
- interaction;
- visualization truth;
- non-grading;
- core-loop usability.

This phase may begin before participant-owned manuscript retention is authorized.

---

## PHASE B — PARTICIPANT-OWNED WORK BETA

Use a participant's real Work only after all of these are true:

1. actual system retention behavior is known;
2. storage location is known;
3. deletion behavior is known;
4. MAIA reading retention is known;
5. logs/telemetry behavior is known;
6. training/use policy is accurately stated;
7. participant receives plain-language disclosure;
8. participant gives the appropriate explicit consent;
9. participant may choose sample material instead.

This phase tests:
- emotional ownership;
- real recognition;
- real curiosity;
- trust with personally meaningful material.

---

# 5. Participant Manuscript Ruling

Until Phase B requirements are satisfied:

> **Do not put ordinary beta participants' private manuscripts into a test environment whose persistence/retention behavior cannot be accurately disclosed.**

Use controlled material instead.

This is not a claim that participant manuscript retention is forbidden forever.

It means:
> **we do not ask for trust before we can truthfully describe the system.**

---

# 6. Facilitator Notes vs System Retention

These are separate consent surfaces.

## Facilitator research notes
May include:
- behavior;
- quotes;
- usability findings;
- participant ID;
- minimal excerpts when necessary.

Governed by research consent/retention.

## Product/system data
May include:
- uploaded manuscript;
- MAIA readings;
- observations;
- revisions;
- declared structure;
- history;
- telemetry/logs.

Governed by product/system data policy.

> **Consent to research notes does not constitute consent to system persistence of a manuscript or MAIA reading.**

---

# 7. Default Beta Data Posture

For the first controlled beta:

- prefer fixture / authorized manuscripts;
- use participant IDs;
- collect minimum research data;
- do not use participant writing for model training;
- do not route writing to new providers merely for beta;
- do not persist participant-owned Work unless the exact persistence policy is disclosed and consented;
- do not claim session-only processing unless the environment actually guarantees it.

If the implementation cannot guarantee ephemeral processing, do not describe it as ephemeral.

# 8. Seedable Beta Environment Requirement

Before R9, create or authorize a reproducible beta environment capable of instantiating:

### Work A — ordinary
- 12 chapters
- declared textual entities
- at least one member-declared theme
- at least one MAIA observation
- Continuity Map data
- coverage data

### Work B — stale
- reading at version N
- Work at version N+1
- known changed passage
- frozen evidence from N
- current passage from N+1
- known timestamps

### Work C — under-covered
- only subset read
- honest coverage gaps
- a cross-Work question MAIA must refuse or narrow

### Work D — read / nothing admissible
- completed reading
- zero admissible observations for target lens

### Work E — not read
- no reading for target lens

The environment must be resettable.

A facilitator should not manufacture these states manually for each participant.

# 11. Facet Beta Preconditions

Before Task 9 becomes READY:

## Same input
- exact same Work;
- exact same locus;
- exact same observation id;
- exact same evidence.

## Guided
Expected visible difference:
- plain-language support;
- suggested next moves;
- more relational translation.

## Learning
Expected visible difference:
- craft explanation;
- technique/evidence connection;
- no additional authority.

## Direct
Expected visible difference:
- concise technical/detail response;
- minimal explanatory framing.

## Must remain identical
- observation truth;
- evidence;
- coverage;
- return address;
- proposal breadth;
- mutation permissions;
- amount of text MAIA may replace/write;
- final Apply boundary.

A label-only facet switch FAILS readiness.

---

# 12. Persistence Beta Preconditions

Before any task tests "find it later":

The object must have:
- durable id;
- owner;
- Work id;
- Work version/read identity where relevant;
- exact address;
- provenance;
- creation timestamp;
- persistence store;
- retrieval path;
- delete/edit semantics;
- authorization boundary.

This applies to:
- member observations;
- applied revisions;
- History;
- declared maps;
- selected templates;
- MAIA readings.

---

# 13. Research Evidence Law

Every beta finding must name the product condition under which it was observed.

Example:

```text
candidate commit
environment
fixture/work id
task
capability readiness
device
viewport
text scale
```

If a task was run before its capability was ready:

> **mark the observation INVALID FOR PRODUCT USABILITY CONCLUSION.**

Do not carry it into synthesis as a defect.
