# SOULLAB WRITER'S STUDIO
# Core Object + State Model Canon v1

Status: FLAGSHIP PRODUCT / DATA-SEMANTICS AUTHORITY  
Purpose: define the minimum shared product objects and lifecycle states Writer's Studio uses so Write, Develop, Review, MAIA, persistence, History, freshness, and beta fixtures cannot invent incompatible meanings.

This canon is additive to:
- Durable Place + Observation Address Canon
- Failure, Recovery + Concurrency Canon
- Work Navigation + Discovery Canon
- MAIA Relational Conversation + Facet Canon
- Language + Microcopy Canon
- Flagship Evidence + Readiness Canon
- existing authorship / provenance / coverage law

It does not authorize schema changes, migrations, implementation, provider changes, merge, or deployment.

---

# 1. North Star

> **Every durable thing in Writer's Studio should have one clear identity, one clear owner/source, one clear relationship to the Work, and one truthful lifecycle.**

The product should never have three different "observation" concepts that only happen to share a label.

---

# 2. Minimal Shared Object Set

The flagship requires a coherent model for at least:

1. Work
2. Work Version
3. Place / Address
4. Reading
5. Coverage
6. Observation
7. Member Observation
8. Relation / Thread
9. Conversation Seam
10. Revision Proposal
11. Applied Mutation
12. History Entry
13. Member Declaration
14. Template Choice
15. Resume State
16. Review Trail
17. Async Request

Not every object must be stored in the same place.
Not every object is necessarily durable.

But every feature must know which object it is operating on.

---

# 3. WORK

A `Work` is the member's authored project.

Examples:
- a book;
- memoir;
- novel;
- nonfiction manuscript;
- teaching text.

Minimum semantic identity:
- Work id;
- owner / access authority;
- title;
- current version identity;
- created/updated timestamps where lawful.

Work is not:
- a chat thread;
- a reading;
- a file upload;
- a single chapter.

---

# 4. WORK VERSION

A `Work Version` is a specific authored state of the Work.

It must support truthful answers to:

- What did MAIA read?
- What did this proposal target?
- What changed after Apply?
- Is this finding stale?
- Can Undo restore the prior state?

A Work Version should not be inferred only from wall-clock time if stronger version identity exists.

---

# 5. PLACE / ADDRESS

A `Place` is a recoverable relationship to authored material.

It may include:
- Work id;
- Work version;
- part/chapter/section identity;
- local content identity;
- span/range;
- resolution state.

Place is not merely:
> character offset

See Durable Place + Observation Address Canon.

---

# 6. READING

A `Reading` is a governed MAIA act over a declared scope of the Work.

It must retain:
- reading id;
- Work id;
- Work version/read version;
- authorized scope;
- facet does NOT alter scope;
- provider/model provenance where required by governance;
- created/completed timestamps;
- status;
- coverage.

A Reading is not:
- an observation;
- a conversation;
- a Review card.

One Reading may yield zero, one, or many admissible observations.

---

# 7. READING STATES

A Reading may be:

```text
REQUESTED
AUTHORIZED
PENDING
COMPLETE
FAILED
CANCELLED
SUPERSEDED
STALE
PARTIALLY_STALE
HISTORICAL
```

These states must not collapse.

`COMPLETE` does not mean:
> observations were found.

A complete reading may yield zero admissible observations.

---

# 8. COVERAGE

`Coverage` states exactly what the Reading included.

Coverage answers:
- chapters read;
- sections read;
- passages read;
- whole-Work vs partial;
- what was not read.

Coverage is factual.

Coverage is not:
- confidence;
- quality;
- importance.

---

# 9. OBSERVATION

An `Observation` is an admitted, evidence-bearing statement about the Work.

Minimum semantics:
- observation id;
- source/provenance;
- Work id;
- reading id where MAIA-produced;
- exact evidence place(s);
- current return place where resolvable;
- coverage;
- wording;
- doesNotEstablish;
- created timestamp;
- freshness.

Observation must not exist without admissible support.

---

# 10. OBSERVATION PROVENANCE

At minimum distinguish:

```text
TEXT_FACT
MEMBER_DECLARED
MEMBER_SELECTED_TEMPLATE
MEMBER_OBSERVED
MAIA_OBSERVED
```

These are not interchangeable.

For example:

> **YOU NAMED THIS**

must not be derived from:
> member selected a prebuilt Spiral template.

---

# 11. MEMBER OBSERVATION

A `Member Observation` is authored by the member.

Kinds:
- Something I noticed
- A question
- A possibility

It retains:
- member authorship;
- exact creation place;
- Work version;
- wording;
- creation/edit timestamps;
- current resolution state;
- deletion/edit semantics.

It is not generated by MAIA.

It may later become related to MAIA observations, but provenance remains member-owned.

---

# 12. MAIA OBSERVATION

A `MAIA Observation` is admitted from a Reading.

It must retain:
- reading identity;
- evidence;
- coverage;
- provenance;
- uncertainty/limits;
- freshness.

Changing facet never creates a new observation solely because rendering changes.

---

# 13. OBSERVATION STATES

An Observation may be:

```text
CURRENT
PARTIALLY_STALE
STALE
HISTORICAL
DISMISSED_FROM_VIEW
ADDRESS_AMBIGUOUS
ADDRESS_MISSING
SUPERSEDED_BY_NEW_READING
```

Do not use:
`RESOLVED`
unless the member explicitly creates that semantic and product law defines it.

MAIA not repeating a finding after reread does not mean:
> fixed.

---

# 14. RELATION / THREAD

A `Relation` connects meaningful places or observations.

Examples:
- same phrase recurrence;
- member-declared relation;
- same entity;
- evidence-backed thematic recurrence;
- observation ↔ related passage.

Minimum semantics:
- relation id;
- source;
- endpoints;
- evidence where MAIA-generated;
- coverage;
- provenance;
- created timestamp.

A Relation is not automatically a theme.

---

# 15. THREAD

A `Thread` is a member-visible path through multiple related places.

Example:

```text
river image
→ Ch 2
→ Ch 6
→ member observation
→ MAIA observation
```

A Thread may be:
- member-created;
- MAIA-suggested;
- system-derived from literal recurrence.

Do not silently convert MAIA suggestion into member structure.

---

# 16. CONVERSATION SEAM

A `Conversation Seam` binds MAIA dialogue to:

- Work;
- Work version/context;
- current locus;
- observation or member intent;
- facet;
- return relationship.

It is not a free-floating chatbot conversation.

Facet switches preserve the seam unless the member intentionally changes subject/place.

---

# 17. CONVERSATION STATES

A Conversation Seam may be:

```text
ACTIVE
BACKGROUND
CLOSED
HISTORICAL
STALE_CONTEXT
```

A closed UI surface does not necessarily destroy the seam.

A dismissed mobile sheet is not automatically:
> cancelled conversation.

---

# 18. REVISION PROPOSAL

A `Revision Proposal` is a non-authoritative possibility.

It must retain:
- proposal id;
- source Work version;
- exact source place;
- proposal text;
- direction label;
- what was preserved;
- what changed;
- created timestamp;
- status;
- MAIA/member provenance.

Proposal is not authored Work until Apply.

---

# 19. PROPOSAL STATES

```text
PROPOSED
VIEWED_IN_CONTEXT
DECLINED
APPLIED
SUPERSEDED
STALE_TARGET
```

`PROPOSED` does not mean:
> recommended.

`DECLINED` is neutral.

---

# 20. APPLIED MUTATION

An `Applied Mutation` is an authorized authored change to the Work.

It retains:
- mutation id;
- Work id;
- pre-version;
- post-version;
- place;
- pre-image;
- post-image;
- actor;
- proposal id where relevant;
- timestamp;
- undo/revert relation.

This is the actual authorship boundary.

---

# 21. HISTORY ENTRY

A `History Entry` is the truthful member-facing record of authored change.

It may represent:
- applied revision;
- manual change where product tracks it;
- undo/revert;
- restore.

History is not merely a rendered list.

It is derived from real mutation lineage.

---

# 22. UNDO / REVERT

Undo creates a new truthful state.

It does not erase history.

Semantics:

```text
V1
→ Apply M1
→ V2
→ Undo/Revert M2
→ V3 (content may equal V1)
```

The lineage still records M1 and M2.

---

# 23. MEMBER DECLARATION

A `Member Declaration` is something the member explicitly names about the Work.

Examples:
- theme;
- intention;
- section purpose;
- relationship;
- structural meaning.

It retains:
- member authorship;
- wording;
- scope/place;
- created/edited timestamps.

MAIA may refer to it.

MAIA may not silently rewrite it as her own ontology.

---

# 24. TEMPLATE CHOICE

A `Template Choice` records member adoption of a supplied framework.

Examples:
- Spiral template;
- another lawful structure template.

Provenance:

> **YOU CHOSE THE SPIRAL TEMPLATE**

not:

> **YOU NAMED THIS**

unless the member separately named it.

---

# 25. RESUME STATE

A `Resume State` exists only to help the member return.

Possible contents:
- Work id;
- mode;
- chapter/section;
- meaningful locus;
- recent member observation;
- unfinished conversation pointer where lawful;
- timestamp.

It should not become exhaustive behavioral logging.

Store minimum necessary.

---

# 26. REVIEW TRAIL

A `Review Trail` preserves how the member moved:

```text
Review
→ observation
→ passage
→ conversation
→ related passage
→ return
```

It retains:
- origin;
- observation;
- current locus;
- branch;
- return state.

Review Trail is navigation state, not necessarily long-term history.

---

# 27. ASYNC REQUEST

An `Async Request` is the execution identity for:
- reading;
- explanation;
- alternatives;
- related passage lookup;
- teaching;
- refresh.

It binds:
- request id;
- Work/version;
- locus;
- observation/member intent;
- requested scope;
- action type;
- created time;
- status.

See Failure, Recovery + Concurrency Canon.

---

# 28. EPHEMERAL / DURABLE / CUSTODIED

Every object must declare one persistence class.

## EPHEMERAL
Needed only for current interaction.

Examples:
- open drawer;
- temporary hover;
- unsubmitted selection.

## DURABLE
Expected to survive session boundary.

Examples likely include:
- member observation;
- Work version;
- applied mutation;
- member declaration.

## CUSTODIED HISTORICAL
Retained because it supports truth/provenance/history.

Examples may include:
- historical reading;
- historical observation evidence;
- mutation lineage.

Exact implementation/retention policy remains governed separately.

---

# 29. OWNERSHIP / SOURCE

Every durable object answers:

> **Whose act is this?**

Possible sources:
- member;
- MAIA;
- system;
- imported source;
- template.

Do not infer author from current renderer.

---

# 30. WORK BINDING

Every Work-derived object must bind to exact Work.

No observation, proposal, history item, conversation seam, or reading may float across Works.

This is a critical isolation boundary.

---

# 31. VERSION BINDING

Historical objects bind to the Work version they actually witnessed/changed.

Current resolution may point forward.

Historical identity must remain intact.

---

# 32. CURRENT VS HISTORICAL

The product must be able to render both:

### What existed then
historical evidence / version.

### What exists now
current Work.

Never overwrite "then" with "now" merely to keep the UI simple.

---

# 33. OBJECT RELATIONSHIP EXAMPLE

```text
Work W1
  ↓
Version V12
  ↓
Reading R7
  ↓
Coverage C7
  ↓
Observation O44
  ↓
Evidence Place P17
  ↓
Conversation Seam S9
  ↓
Proposal RP3
  ↓
Applied Mutation M22
  ↓
Version V13
  ↓
History H22
```

Later:

```text
O44
→ current resolution P21
→ status STALE
```

The old evidence P17 still exists historically.

---

# 34. MEMBER OBSERVATION EXAMPLE

```text
Work W1
Version V13
Place P21
        ↓
Member Observation MO8
kind = QUESTION
"Is this where Clara finally trusts the river?"
```

Later MAIA may respond:

```text
Conversation S12
bound to MO8 + P21
```

MAIA's answer does not change MO8 authorship.

---

# 35. FIRST ARRIVAL / RETURN EXAMPLE

If Resume State exists:

```text
Resume RS4
Work W1
mode = Write
chapter = 6
place = P21
```

Product may say:

> **You last worked in Chapter 6.**

It may not infer:
> **You were struggling with Clara's motivation.**

unless that was explicitly persisted as member intent and lawful to reuse.

---

# 36. STALE READING EXAMPLE

```text
Reading R7
Work version V12

Current Work version V15

Observation O44
evidence = V12/P17
current resolution = V15/P25
freshness = STALE
```

UI may show:
> **MAIA noticed this in an earlier version.**

Then:
- Show original
- Show current
- Read again

---

# 37. READ-AGAIN SEMANTICS

`Read again` creates:

```text
Reading R8
```

It does not overwrite:
```text
R7
```

New observations receive new identities where they are genuinely new admissions.

Old observation history remains truthful.

---

# 38. DUPLICATION LAW

Do not create duplicate durable objects because the same UI renders twice.

Rendering is not object creation.

Examples:
- switching facet ≠ new observation;
- opening Review ≠ new reading;
- reopening History ≠ new mutation;
- revisiting passage ≠ new member observation.

---

# 39. DERIVATION LAW

Derived UI labels must not become authoritative stored truth unless product semantics require it.

Example:
> "Often"

may be derived from occurrence count.

Do not persist "Often" as the primary fact if the actual fact is:
> 7 addressed occurrences.

Store truth at the strongest factual layer.

---

# 40. NO SHADOW OBJECTS

If one concept has multiple runtime representations, they must point to one canonical product identity.

Avoid:
- `reviewFindingId`
- `maiaInsightId`
- `patternCardId`

all referring to the same Observation with no declared relationship.

UI ids may differ.
Product identity must not.

---

# 41. NO STATUS INFERENCE FROM UI

Do not infer object lifecycle from:
- card color;
- open/closed drawer;
- current route;
- visible text.

Lifecycle state is explicit.

---

# 42. DATA MINIMIZATION

Do not make everything durable merely because it can be stored.

Ask:

> Does this need to survive to keep authorship, trust, return, or provenance truthful?

If not:
- prefer ephemeral.

Examples typically ephemeral:
- hover state;
- temporary tab expansion;
- unsent draft prompt;
- transient highlight.

---

# 43. DELETE / DISMISS / HIDE / UNDO

These are distinct verbs.

## DELETE
Remove an object where law permits.

## DISMISS
Remove from current attention/view.

## HIDE
Suppress display, potentially reversible.

## UNDO
Create an authored state that reverses a prior mutation.

Never use one implementation for all four without product-semantic review.

---

# 44. REQUIRED CROSS-OBJECT INVARIANTS

## OI1 — WORK ISOLATION
Objects never cross Work boundary accidentally.

## OI2 — VERSION TRUTH
Historical objects retain exact version identity.

## OI3 — PROVENANCE TRUTH
Member/MAIA/system/template sources remain distinct.

## OI4 — OBSERVATION IDENTITY
Facet/render changes never mint new observation truth.

## OI5 — READING ≠ OBSERVATION
A reading may have zero observations.

## OI6 — PROPOSAL ≠ MUTATION
Proposal text does not alter Work until Apply.

## OI7 — UNDO ≠ ERASE
History remains truthful after Undo.

## OI8 — CURRENT ≠ HISTORICAL
Forward resolution never overwrites original evidence.

## OI9 — EPHEMERAL ≠ DURABLE
UI does not imply persistence falsely.

## OI10 — DISMISS ≠ DELETE
Attention state does not falsify custody.

## OI11 — RENDER ≠ CREATE
Re-rendering does not mint duplicate product objects.

## OI12 — RESUME MINIMIZATION
Return support does not become exhaustive surveillance.

---

# 45. Defeat Candidates

### D-OI1
Opening the same MAIA observation in Guided mints a new observation id.

### D-OI2
Reread overwrites the old reading record.

### D-OI3
A proposal is stored directly as authored manuscript before Apply.

### D-OI4
Undo deletes the Apply history entry.

### D-OI5
Member observation later renders as MAIA-authored.

### D-OI6
A Review card id becomes the only identity for an observation.

### D-OI7
A stale observation's evidence is replaced with current wording.

### D-OI8
Session-only note visually says "Saved with this passage."

### D-OI9
Dismiss finding permanently deletes historical reading evidence.

### D-OI10
One Work's observation attaches to another Work after navigation.

### D-OI11
Resume state stores every click/scroll forever.

### D-OI12
`Often` is stored without the underlying count/evidence that produced it.

# 47. Implementation Priority

Do not build a grand universal knowledge graph.

Build the minimum coherent object substrate necessary for:

- observation address durability;
- first-arrival/return truth;
- member observations;
- stale readings;
- revision/history;
- Review trails;
- beta fixtures.

Generalization follows proven need.

---

# 48. Product Status Law

An object type may be:

```text
SPECIFIED
IMPLEMENTED
PERSISTED
ROUND-TRIP WITNESSED
HUMAN-VISIBLE
ADMITTED
```

These states follow the Flagship Evidence + Readiness Canon.

Do not call the object "done" because the type exists.

---

# 49. Product Principle

> **The product should remember the things required to preserve authorship and relationship — and forget the things that are merely interface noise.**

---

# 50. Spirit of Soullab

The object model should produce an experience in which:

> My Work remains mine.
>
> My observations remain mine.
>
> MAIA remembers what she actually read.
>
> A possibility is not a change until I choose it.
>
> History tells the truth.
>
> Old evidence stays old evidence.
>
> Current writing stays current writing.
>
> I can leave and return without the system inventing a story about me.

**A deeper you. A more human world.**
