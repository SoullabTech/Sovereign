# Practitioner Portal — Discovery Prompt Library

> Founder-directed 2026-08-05 (evening). This library replaces the original eight-prompt
> architecture-discovery queue. Reconciliation against ratified canon showed that three of the
> eight re-asked questions the founder had already ruled, and one violated a standing gate.
>
> **Process rule (adopted 2026-08-05):**
> **Discovery agents may discover unknowns. They may not rediscover settled foundations.**
> The value of a discovery prompt is proportional to the uncertainty that remains. If a founder
> ruling has already resolved the uncertainty, a discovery prompt becomes a mechanism for
> creating competing constitutions. This is the architectural equivalent of the code rule
> against rebuilding merged work — it keeps the project cumulative.

## Governing design criterion (founder, 2026-08-05)

Every Practitioner Portal function must answer:
**"How does this help the practitioner succeed, grow, or evolve?"**

- **Succeed** (outward-facing — deliver the work): client relationships, scheduling, session
  preparation, notes, programs, courses, workbooks, books, workshops, retreats, assessments,
  communication, publishing.
- **Grow** (inward-facing — develop): wisdom cultivation, reflection, integration of new
  learning, distinctions, questions, stories, practices, research, certification learning,
  reading, journaling, voice capture, source integration (Obsidian etc.).
- **Evolve** (developmental — the layer almost no software supports): seeing how thinking has
  changed over time; revisiting old ideas in light of new experience; recurring themes across
  years; connecting coursework with lived coaching; tracking a distinction from first capture to
  published offering; reflecting on abandoned practices; seeing where the work becomes more
  coherent. Evolution is not adding information — it is changing the practitioner.

The portal organizes into **three developmental domains**, not modules:

| Domain | Sentence | Contents |
|---|---|---|
| **Practice** | Help me become a better practitioner | wisdom · craft · reflection · learning · research · development |
| **Creation** | Help me bring my work into the world | books · courses · workbooks · programs · talks · retreats · assessments · publishing |
| **Relationships** | Help me accompany people well | clients · groups · organizations · session prep · follow-through · between-session support |

Everything else (billing, settings, integrations, documents) is infrastructure — necessary,
secondary. A feature answering none of succeed/grow/evolve probably does not belong in the core
product.

**Relation to existing canon:** this extends — does not replace — the standing practitioner-side
feature filter (*"every feature should either help a practitioner grow in wisdom or help them
faithfully offer wisdom they have already grown"*). The "Evolve" domain corresponds to the held
**practitioner development mirror** and **craft cultivation** directions, and inherits their
constraint: practitioner's OWN material only (aggregation ruling Path A); never analytics or
scoring; reflective material for the practitioner alone.

## Prompt A — Six-Month Stewardship Environment (RUN FIRST)

The only active architecture-discovery prompt. Expected output is **a six-month build plan, not
an architecture**.

```text
Read these documents FIRST and treat them as BINDING settled law — cite them where a question
is already ruled; do not re-derive:

1. docs/specs/PRACTITIONER_WISDOM_FIELD_PRODUCT_DEFINITION_v0.md — the constitution
   (three layers Commons→Development→Wisdom; three axes; layer-promotion gate; §12).
2. docs/governance/PRACTITIONER_FIELD_AUTHORITY_SCHEMA.md — the authority model.
   Do NOT redesign it.
3. docs/reviews/LARRY_IP_CORPUS_INVENTORY_AUDIT_2026-08-03.md — the Larry IP audit.
   Ground truth: zero Larry-authored (Class A) sources located anywhere; rights agreement
   exists and is UNSIGNED; Attachment A is deliberately empty.
4. docs/governance/PRACTITIONER_WISDOM_CAPTURE_PROTOCOL_v1.md — how the first governed
   source comes into being (the sitting).
5. Ratified living-source rulings (2026-08-05):
   - Cultivation lifecycle: Captured → Connected → Reflected on → Practiced → Refined →
     Approved → Available to clients. Readiness-to-offer is the LAST step, never the first.
   - Three independently-evolving layers: source adapters ⊥ stewardship ⊥ expression.
   - Five human acts precede ANY ingestion: signed agreement → authorized sitting →
     captured source record → classification → ratification.
   - The practitioner field is a practice of becoming, not a repository of answers.
6. Design criterion: every function must help the practitioner succeed, grow, or evolve
   (see the domain table in this library).

THE QUESTION (the founder's own scope ruling, 2026-08-05):
Given everything already ratified, what is the smallest stewardship environment that
genuinely helps Larry succeed, grow, and evolve over the NEXT SIX MONTHS — during Harvard
Positive Psychology coursework, real coaching, real reflection, real revisions?

Constraints:
- Six months, not five years. Let the next capability be earned by use.
- NO ingestion of Larry material and no Larry-specific content claims — the BUILD GATE and
  the unsigned agreement hold. Design the environment that will RECEIVE the first governed
  source after the sitting; do not assume it exists.
- Weekly and monthly workflows grounded in the cultivation lifecycle.
- Only explore what remains undecided. Where a ruling settles a question, cite it.

THE DEVELOPMENT TEST (founder, 2026-08-05 — every proposed capability must answer ALL FOUR):
1. How does this help the practitioner SUCCEED? (deliver better work · serve clients more
   faithfully · create sustainable offerings)
2. How does this help the practitioner GROW? (learn · integrate · reflect · develop wisdom)
3. How does this help the practitioner EVOLVE? (change over time · mature their craft ·
   refine understanding · become a different practitioner than six months ago)
4. WHY IS THIS NEEDED IN THE NEXT SIX MONTHS? If it isn't needed during Larry's actual next
   six months, it belongs in the backlog, not the build plan. This question keeps the plan
   grounded in reality instead of designing for an imagined future platform.

Output — a six-month build plan, directly actionable, NOT a narrative:
- A priority table:
  | Priority | Capability | Why now | Success / Growth / Evolution | Evidence that unlocks next step |
- NEGATIVE RECOMMENDATIONS, first-class: "do NOT build these yet, and here is why" — the
  not-yet decisions preserve focus and are as valuable as the build rows. Each carries the
  evidence or human act that would reactivate it.
- Weekly workflow / monthly workflow for Larry.
- Which existing substrate is reused (capabilities 1–4 are substantially built; assessments
  is the only true greenfield).
- Every row cites the ruling or document that grounds it.
```

**Positioning note (founder):** this is not a "Practitioner Portal" in the CRM/LMS/CMS/KM
sense. The design object is **a developmental operating environment for people whose life's
work is helping other people develop.**
